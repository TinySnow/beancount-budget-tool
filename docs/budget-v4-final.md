# Budget v4：预算、用途与持有的最终语义架构

状态：**2026-10-09 冻结的 v4 架构规范；生产内核尚未实现**。本文是实施语义的唯一依据，吸收了两轮独立复审和最终采纳复审；旧稿与审校记录不再是规范的一部分。冻结的意思是：本项目按本文解释已接收的输入，并按本文拒绝不支持的输入；不是声称代码已经通过验收，也不是承诺任何记错的账都能被程序识破。修正笔误可以保留 v4；改变已签发数字的含义、放宽拒绝边界或增加隐藏推断，必须显式升级 schema、迁移数据并补回归测试。

## 1. 先说人话：四个不同的问题

假设十月给“生活费”安排 2000 元，同时打算给“储蓄”存 900 元。这不是一笔 2900 元的统一预算，而是两项不同承诺：

| 问题 | v4 的答案 | 不代表什么 |
|---|---|---|
| 生活费还能花多少？ | `R = P + S − E`：月计划 + 明确收入补充 − 净费用 | 银行里一定有这笔现金 |
| 储蓄本月按计划存够了吗？ | 月目标 `Q` 对比本月**净划拨** `G` | 储蓄账户当前余额 |
| 储蓄现在实际在哪里？ | `H`：每个账户、商品、成本批次的储蓄原生份额 | 这些资产都属于“自有本金”或随时可花 |
| 这笔钱属于哪个专题？ | `tracking`：可重叠的检索索引 | 一种可以与前三项相加的金额 |

`E/S/G` 是期间流量，`H` 是截止时点的存量。退款写负 `Expenses` 就是负 `E`，并不伪装成 `Income`；收入补充增加 `S`，不冲减已支出。`G` 只表示从 v4 起点以来主动划给某用途的净额，允许负数，不叫“用途本金”或“自有资金”。借款现金也能归某用途，但 v4 不计算扣债后的“自由现金”。信用卡消费在刷卡时进 `E`，还卡本身不再进 `E`。

公式只有四条，且每条有自己的来源：

```text
E[桶,期间] = Σ 该桶已分类 Expenses 切片的有符号历史价值
S[桶,期间] = −Σ 该桶已分类 Income 切片的有符号历史价值
G[用途,期间] = Σ 主动进入该用途的边界价值 − Σ 主动离开该用途的边界价值
H[用途,账户,lot,时点] = 期初份额 + 已booked资产切片的原生变化 + 独立归属转移的原生变化
```

完整月份的 `R=P+S−E`；每个切片在**同一投影**只贡献一次。`H` 的归属转移只计归属变化，不生成第二份真实资产。`G` 只由认证过的边界事件生成，不能把所有正资产腿相加。专题查询只筛上述记录，不改变公式。

**准确性边界**：给定一份完整、loader 验证通过的财务事实，以及 v4 所要求的明确分类、归属、组和计价证明，每个已签发的数字有且只有一种计算方式；证据不够就拒绝签发。金额写错但仍配平、或整笔没有导入，属于录入/importer 和人工对账责任，不属于预算架构能独立发现的错误。明确写错的用途意图也不能凭数学自动识破，因此审阅界面必须让人核对每笔对 `E/S/G/H` 的影响。

## 2. 日常怎么写

下面的账户均假定已在账本中 `open`，涉及划出时已存在足够的期初用途份额。代码块是独立示例，不是把它们直接连起来就能形成真实账本。**Beancount posting 后面的 metadata 属于该 posting；首个 posting 前面的 metadata 属于交易。** `budget` 和 `fund` 只能写在具体 posting 上，`tracking` 可以写在交易或 posting 上。`comment` 等你自己的 metadata 原样保留。

### 2.1 购物、退款与额外收入

```beancount
2026-10-01 * "买菜"
  Expenses:Food 300 CNY
    budget: "生活费.餐饮"
  Assets:Daily -300 CNY
    fund: "-"

2026-10-03 * "退款"
  Expenses:Food -100 CNY
    budget: "生活费.餐饮"
  Assets:Daily 100 CNY
    fund: "-"

2026-10-04 * "奖金拿出50元补生活费"
  Income:Bonus -50 CNY
    budget: "生活费"
  Assets:Daily 50 CNY
    fund: "-"
```

`E(餐饮)=200`，`S(生活费)=50`。退款发生在哪个月，就在哪个月记负 `E`；该月没有原购买也合法。若同一到账还有独立奖励，可另写一条 `Income`；**不能仅凭负费用与收入同时存在就断言双计**。`budget:"-"` 明确表示费用或收入不参加消费预算，不等于 0 元。

### 2.2 把钱存入储蓄，然后从 A 搬到 B

```beancount
2026-10-05 * "首次划给储蓄"
  Assets:Daily -1000 CNY
    fund: "-"
  Assets:SaveA 1000 CNY
    fund: "储蓄|划拨"

2026-10-06 * "储蓄搬家"
  Assets:SaveA -1000 CNY
    fund: "储蓄"
  Assets:SaveB 1000 CNY
    fund: "储蓄"
```

第一笔 `G(储蓄)+1000`，第二笔 `G=0`，只是 `H` 从 A 搬到 B。`fund:"-"` 是明确的“未指定用途”份额 `U`，不是“没有分析”。漏掉 A 的储蓄来源、或把 B 再写成 `|划拨`，不能靠整笔会计配平掩盖。

### 2.3 利息、购物、还卡

```beancount
2026-10-08 * "储蓄利息仍留在储蓄"
  Income:Interest -10 CNY
    budget: "-"
  Assets:SaveB 10 CNY
    fund: "储蓄|损益"

2026-10-09 * "用储蓄买日用品"
  Expenses:Daily 300 CNY
    budget: "生活费.日用品"
  Assets:SaveB -300 CNY
    fund: "储蓄|划拨"

2026-10-12 * "刷卡买菜"
  Expenses:Food 300 CNY
    budget: "生活费.餐饮"
  Liabilities:Card -300 CNY

2026-11-03 * "用储蓄还卡"
  Liabilities:Card 300 CNY
  Assets:SaveB -300 CNY
    fund: "储蓄|划拨"
```

利息让储蓄 `H+10、G=0`；储蓄购物让 `E+300、G−300、H−300`；刷卡时 `E+300`，十一月还卡 `E=0、G−300、H−300`。若购物退款重新存回储蓄，负费用腿贴原消费桶、资产正腿贴 `储蓄|划拨`；若退款留在普通账户，资产腿写 `fund:"-"`，储蓄不会凭退款自动恢复。

### 2.4 证券卖出并决定把收益撤出：分两步表达

证券买卖有成本权重、实际成交价、手续费和收益，不能把它们混成一个数。首版 v4 **不自动解释“F 的证券卖出，现金直接标 U”**这种复合交易；先使卖出所得仍归 F，再用一件用途转移表达撤出（以下示例另假定该账户此前已存在 10 TEST、成本 10 CNY 的 lot）：

```beancount
2026-10-20 * "卖出，所得先留在投资用途"
  Assets:Stock -10 TEST {10 CNY} @ 12 CNY
    fund: "投资"
  Assets:Broker 119 CNY
    fund: "投资"
  Expenses:Fee 1 CNY
    budget: "投资费用"
  Income:Gain -20 CNY
    budget: "-"
```

这笔的财务成本权重是 `−100+119+1−20=0`；投资用途 `G=0`，`H` 从 10 TEST 变为 119 CNY，费用 `E=1`。该示例**不落在 §4.3 的自动模板内**（模板 5 明确排除带费用/收入对手的交易），因此必须生成一件显式 `GroupMembership`，把两条资产切片与 `Expenses:Fee`、`Income:Gain` 作为组内证据引用；费用和收益的**用途归因**在审阅界面确认，**同笔含费用/收益对手时一律需要这件显式组**，不能按比例猜。若随后要把到手的 119 CNY 全部退出投资，记录一件“同账户、同商品、投资→U、119 CNY”的 `OwnershipTransfer`，产生 `G(投资)−119`；真实证券买卖分录不再计第二遍。若原账本把卖出现金直接标 U，迁移时须先改其**预算归属**为投资，再增加转移事件；财务 posting 的账户、金额、日期、成本不能偷偷改变。

## 3. 三个键的精确语法：标签声明意图，证据只能证伪

| 键 | 合法位置和值 | 确定语义 |
|---|---|---|
| `budget` | `Expenses`/`Income` posting；一个已注册桶名或 `-` | 桶名解析为稳定 ID；Expenses 进有符号 `E`，Income 的反号进 `S`；`-` 不进预算 |
| `fund` | `Assets` posting；`-`、已注册用途名、`用途\|划拨`、`用途\|损益` | 用途名解析为稳定 ID；`-` 属 U；裸用途指用途内持有变化；`划拨` 指主动跨用途边界；`损益` 指有外部原因的非划拨持有变化 |
| `tracking` | 交易或 posting；半角逗号分隔的已注册专题名集合 | 解析为专题 ID；仅选择明细，不产生预算事实 |

`fund:"用途|期初"` 在 v4 增量账本中**非法**；期初只在独立快照中表达。空值、多于一个 `|`、未知后缀、未经注册的名字、重复 metadata 键都拒绝。`fund` 的原因是**用户的权威声明**：程序按它尝试对应的经济组，不会因为别的组看起来也能配平而暗中改判。证据不足则报错；同一会计事实改了标签，属于改了预算输入，数字可以改变，但必须重新校验。

`|损益` 不是“让 G 不动”的逃生门。唯一可自动识别的简单形式是同交易**一条**带 `|损益` 的现金资产腿与**一条**明确的 `Income` 证据相配，金额/币种/方向完全闭合，例如 §2.3 的利息。投资手续费、亏损核销、公司行为等必须有显式类型化组及证据；一条日用品 `Expenses` 不能仅凭它的存在就让 `储蓄|损益` 成立。普通购物从用途支付用 `|划拨`；如果有人用外部组文件把日用品错称投资手续费，那仍是人的标注错误，架构不能假装自动识破。

cutover 起的每条 `Expenses`/`Income` booked posting 必须由 inline `budget` 或外部 `BudgetClassificationClaim` 的精确分类切片完整覆盖；不能因未标就默认“不参加预算”。两者互斥；外部切片同号、同商品且原生数量精确和等于被认领的 booked posting；多桶费用不得靠一个逗号值让每个桶各取全额。`budget:"-"` 是可审阅的显式选择。原文 posting 如被 booking 拆成多个子腿，应逐个 booked 子腿认证分类，不把原文总量重复认领到每个子腿。

`budget`、`fund` 和 `tracking` 分属独立名册；同一显示名可同时是消费桶和用途。每条标签经**版本化的名字→稳定 ID 映射**解析，映射与名册一起进入快照。名字用 NFC，首尾空白去掉；`.` 是桶/用途层级分隔符，段内不许有 `.`、`|`、`,`、`，` 或控制字符；同一命名空间内名称唯一。改名保留旧名到原 ID 的历史映射，不靠“最相近名字”猜。`tracking` 只用 ASCII 逗号分隔，逐项 NFC/trim/去重；全角逗号在正式运行时拒绝，迁移工具可提案显式改写。专题本身没有总金额：查询时必须选 `E`、`S`、`G` 或 `H` 的**期间变化**等具体度量，不把不同量相加；交易级专题覆盖该交易生成的相关投影行，posting 级仅覆盖该 posting 衍生的行，联合筛选按行 ID 去重。`H` 的期末存量不能凭历史上某次专题标签直接归为该专题。

## 4. 从账本到结果：不再“搜索一个看起来合理的解释”

正式管道如下；每一层只做自己的事：

```text
冻结根账本/include闭包 + v4配置/计划/期初/归属/价格
→ 原文证据采集 + 固定版本官方 Beancount loader/booking
→ 原始posting ↔ booked子腿/生成事实的确定映射
→ 费用/收入分类、资产用途份额、经济事件与计价证明
→ 全量不变量校验 → ValidatedSnapshot
→ TUI / CLI / CSV / JSON 共用同一份投影
```

loader 有任何错误就不签发；**不**因预算层能从原文恢复一个 `@@` 总价而绕开 Beancount 的财务错误。原文层不自己重做会计 booking，只在信息丢失前保留 `@`、`@@`、成本、总成本、重复键、注入指令与来源位置。不能唯一映射原文 posting 到 booked 子腿就拒绝，不能从有限小数单位价猜回原总价。

### 4.1 归属是一个域，配组和计价是另外两个域

cutover 后每条 `Assets` booked 子腿必须有**恰好一份**覆盖其原生数量的用途归属：inline `fund`，或外部 `OwnershipClaim`，不能两边同时决定 owner。一个原始 `+100 CNY` 可切成 F `+60`、U `+40`，但切片必须同商品、同号、精确和为 `+100`；`F+200/U−100` 不合法。已由 inline `fund` 决定 owner 的切片，**允许**被外部组记录引用，以说明它与哪条费用/收益配对；组记录不得重新写 owner 或复制这份数量。费用/收入分类同理：inline `budget` 与外部分类切片二选一，而组证据可以引用已分类的事实，不会使 `E/S` 计两次。

外部文件由迁移/审阅界面生成稳定引用，人确认的是“用途、原因、金额、计价”，不需手敲哈希。引用定义固定为：

```text
RawPostingRef = (相对根账本规范路径, 原始交易文本SHA-256,
                 同一文件内相同交易的出现序号, 原文posting序号)
BookedRef     = (RawPostingRef, booking子序号, 完整LotKey, 已booked事实哈希)
GeneratedRef  = (生成指令RawRef, 生成类型, 生成序号, loader版本)
SliceRef      = (BookedRef或GeneratedRef, 切片序号)
```

上述出现序号、原文 posting 序号、booking 子序号和切片序号均从 **1** 开始，按冻结输入及官方 loader 结果的顺序编号；不是按文件系统枚举顺序。引用还要核对账户、原生数量、商品、lot 和所依赖的事实哈希；相关事实变动后失效待重映射，不能靠裸行号贴到新交易。完整快照哈希用于报告重算与审计，不是所有人工声明的统一失效开关：追加无关交易会生成新快照和新报告，但旧声明若所引用的原文、booked 事实、相关 lot 历史及名册/计价语义均未变，须在新快照中自动重验并沿用原审批；依赖变了则必须重新确认。原文→booked 对应无法唯一验证（包括自动补金额、拆 lot）时拒绝，不猜“第一个相似 posting”。`pad` 的 generated 引用取**生成它的指令**，不取合成 posting 的 `meta.filename/lineno`：后者跨 Beancount 版本并不稳定。loader/插件版本进快照。`^link` 只是关联索引，不能充当去重 ID；相同日期、金额、内容的两笔真实交易照计两次。可靠 importer source ID 冲突时拒绝，但不宣称预算工具能发现整笔漏导入。

侧文件 schema v4 固定为**五类**记录，**不允许一个字段兼做两类记录**。`RawTxnRef` 是 `RawPostingRef` 的前三项。

- `BudgetClassificationClaim {claim: BookedRef|GeneratedRef, slices:[{id, bucket_id|outside, signed_units}]}` 只认领 `Expenses`/`Income`，仅在没有 inline `budget` 时出现；`outside` 等价于显式 `budget:"-"`。一件 claim 覆盖该 booked posting 的全部原生数量，切片 ID 在快照内唯一，不允许另一件 claim 或 inline 标签重复覆盖。
- `OwnershipClaim {claim: BookedRef|GeneratedRef, slices:[{owner, signed_units}]}` 只在没有 inline `fund` 时出现。
- `GroupMembership {id, kind, transaction:RawTxnRef, assets:[SliceRef], evidence:[{posting:BookedRef|GeneratedRef, signed_units, role}]}` 只**引用**已有归属与真实财务证据，不能再写 owner 或 bucket；`EvidenceAllocation` 就是这里的 `evidence` 条目，不是第六类记录。
- `ValuationBinding {target:BookedRef|分类切片ID|边界事件ID, role, report_currency, exact_amount, proof_ref}` 只给一个目标的一个角色绑定一份权威历史价。指向 `BookedRef` 且角色为原文总价分配时，只把被拆开的 `@@` 总额分给 booked 子腿，不与分类切片重复计价；分项精确和必须等于原文总额。`PaymentAllocation` 是一组共用同一支付证据、指向分类切片的此类绑定与守恒校验，不是第六类侧文件记录。
- `OwnershipTransfer {id, after:RawTxnRef|cutover, account, LotKey, from, to, units, valuation:ValuationBinding引用}` 只改变份额，不 claim 财务 posting。

每个 `id` 在快照内唯一，外部记录的 `transaction` 不得跨财务交易；证据分摊与原分录同号且精确和不超出原量。一个 posting 被 inline 归属后仍可出现在 `GroupMembership.assets`，但不能再出现于 `OwnershipClaim`；已分类费用/收入也可作为组证据，组引用不能使 `E/S` 重计。复杂组的完整 source refs、审阅人和事实哈希随报告保存。审阅界面可以让人选择“餐饮 60 USD／旅游 40 USD”并生成记录，不要求人手写引用或 YAML。

例如 §2.4 的“卖出后把 119 元撤出投资”，人只需在界面确认“这笔卖出之后，投资→未指定，119 CNY”；系统生成的归属事件相当于：

```yaml
schema: 4
valuations:
  - id: exit-value
    target: exit-investment-after-sale
    role: boundary
    currency: CNY
    exact_amount: "119"
    proof: native
ownership_transfers:
  - id: exit-investment-after-sale
    after: { transaction: "系统生成的RawTxnRef" }
    account: Assets:Broker
    lot: CNY/no-cost
    from: 投资
    to: "-"
    units: "119 CNY"
    valuation: exit-value
```

`transaction` 引用在落盘时必须是上述结构化 RawTxnRef，不得把示例里的说明文字当有效 ID。执行前确认该 lot 的投资份额至少 119；执行后真实账户总资产不变，投资 `H−119`、U `+119`、投资 `G−119`。同一 `id` 再应用一次必须拒绝，不可二次撤出。

### 4.2 经济事件有哪些端点

三种端点：`OwnedAsset(用途或U,账户,lot)` 是真实资产份额；`FinancialCounterpart(真实posting)` 是 Income、Expenses、Liabilities 或 Equity 等对手证据；`External` 是钱离开/进入用途边界的**概念端点**，不能持有 `H`，也不能凭空制造 U。全部财务 posting 已由官方 loader 配平；预算组把相关切片和对手证据分区，不造额外财务 posting。

| 事件 | 典型写法 | `E/S`、`G`、`H` |
|---|---|---|
| 普通事务 / `BudgetOnly` | 全是 U 资产，或刷卡消费仅 `Expenses+Liabilities` | 分类费用/收入照计；U 随真实资产变；无命名用途 `G` |
| `ExternalFlow` | `Assets U +100 / Liabilities −100` 借款，或 `Assets U +100 / Equity −100` | U 真实增加；本金不进 `E/S/G` |
| 用途内搬移 | A、B 的同用途、同商品/lot 一减一增 | `G=0`，`H` 只换账户；跨月需真实 Transit |
| 投资买卖/换汇 | 同一用途的资产及其明确归属的收益、手续费 | `G=0`，`H` 按原单位变；费用/收入另按预算标签计 |
| 非划拨变化 | `|损益` 与明确的利息/亏损/投资成本证据 | `G=0`，`H` 随实际资产变 |
| 主动边界变化 | `|划拨`，或单一 `OwnershipTransfer` | 命名用途 `G` 有符号变化；`H` 依真实资产及归属转移变化 |

借款本金还款若由 F 资产支付，F 的资产腿明确写 `F|划拨`，组的另一端是**真实 Liabilities posting 与 External 端点**，不会凭空给 U 增加同额库存。无资产腿的信用卡消费通过 `BudgetOnly` 得 `E`，不要求捏造一条资产腿。cutover 后真实 `pad` 或权益调整先作为真实财务事实进入 `ExternalFlow`，其资产归属再由 generated claim 决定，绝不重复增加财务余额。

### 4.3 自动编组只支持有限模板

自动编组**只在一笔已 booked 的交易内**进行，不跨交易搜索，不把 posting 再猜着拆小；切片只能来自明确的归属声明。按以下顺序**逐条判定**（顺序只用于判定与报错定位，**不表示先命中者优先**），而不是枚举任意图：

1. 没有命名用途资产切片：整笔为普通事务；无资产的费用/收入仍正常分类。若所有 E/S 历史价值可证，直接签发，无 `G`。
2. 只有一名用途、一个商品和一个完整 lot，所有该用途的裸 `fund` 资产切片原生数量和为零，且无其他用途、划拨、损益或未解释的费用/收入：编成**一个规范多对多搬移组**。记录全部来源，不宣称哪条转出对应哪条转入；同账户相反腿若有重分类意图，必须写独立归属事件。
3. 一条 `F|划拨` 资产腿，和恰好一条同报告币种、等额反向的 U 资产腿，或一条对应的 `Expenses`/`Income`/`Liabilities` 财务对手腿：编成简单边界组。多个可能对手、外币、带成本证券、费用混合时不用此模板。
4. 一条 `F|损益` 报告币种现金腿，和恰好一条等额反向的 `Income` 证据：编成简单非划拨组。`Expenses`、证券和公司行为均不靠这条简写自动放行。
5. 同一 F 的**恰好两条**裸 `fund` 资产腿、一条现金或外币、一条证券或另一币种，无费用/收入/负债/权益对手，且 booked 成本权重按币种向量精确相抵、lot 唯一：编成简单买入、按成本卖出或换汇组，`G=0`。有收益、手续费、多 lot 或多用途时退出此模板，要求显式组。

模板条件不得同时成立（判定方式见上）；若发生，报 `GROUP_AMBIGUOUS`。剩余的命名用途资产切片必须有**显式** `GroupMembership` 与 `EvidenceAllocation`：它们引用已有 `SliceRef` 和财务对手 posting，不再声明 owner。组只限**同一原始财务交易**；跨月转账由真实 Transit 在各自交易内成组，并用 link 关联生命周期而不跨月抵消。每份资产切片恰好被一个最终事件消费；每份费用/收入证据在**用途归因域**最多使用一次，且显式归因组的使用量不得超过原分录。同一费用作为 `E` 来源、又作为该组的原因，属于不同投影，不算双计。

复杂组必须给出 `kind`、成员、证据、计价角色和守恒证明。凡有多种可行的组型、费用分配或价值来源而无显式选择，一律拒绝，不以“最终总数碰巧相同”为理由猜因果。上述**纯搬移多对多**是唯一允许的等价合并，因为它不涉及额外原因、价格、阶段或 owner，且所有来源集合和逐坐标库存相同。

守恒检查不是一条“总金额等于零”公式，而按组型固定：

| 组型 | 必须核对的等式；不满足则拒绝 |
|---|---|
| 普通事务 / `BudgetOnly` | 官方交易无 error；全部 E/S 分类切片完整且不重复；无命名用途 G。没有资产腿完全合法。 |
| 同用途搬移 | 同一用途、商品和完整 lot 的资产原生切片**代数和为 0**；无被该组消费的外部收益/费用；只改 H 的账户位置。 |
| 投资买卖/换汇、非划拨变化 | 该组资产切片的**成本权重按币种向量**加已分给该组的真实 Income/Expenses 等对手证据，精确等于 0（仅允许 §5 已证明的原文表示修正）；组内每个证据切片最多一次；G=0。多个用途混交易时不自动推断证据分配。 |
| 主动边界变化 | U/其他用途的真实资产切片或 Income/Expenses/Liabilities/Equity 的真实对手证据必须足以解释该组财务变化；进入/离开 F 的**同一个历史边界价值**分别给 G 正/负行，U/External 不产生 G。现金转用途不能靠另一笔无关收入“赞助”。 |
| 独立 `OwnershipTransfer` | 该账户/lot 真实资产净变化为 0；from 足额减、to 同单位加；两端引用同一计价证明；不再次消费财务 posting 或生成第二份 H。 |

组内引用的真实财务 posting 与费用/收入证据分摊都必须在所属**原始交易**内完整结算，不能拿另一笔交易来补这笔的权重差。每个组还须声明它消费了哪些 `SliceRef`，相同切片不能放入两个最终组；全部组的外部资产变化之和必须逐账户/lot 等于原始 booked 资产变化。这样即使一笔里有两个用途、三条费用，守恒也不能靠无关腿相互抵消。

### 4.4 复合交易首版不自动解释

首版 v4 不接收“卖出 F 证券、同一交易的所得现金直接标 U”作为一个自动事件。它必须改为：现金 posting 的**预算归属**先写 F，投资组完成后再写独立 `OwnershipTransfer(F→U)`，如 §2.4。归属事件在同日绑定到“**哪笔已 booked 交易之后**”，核对转移前 F 份额足够、转移后逐账户/lot `A=U+ΣH`。它只改变归属，不生成真实财务数量；转移的两端共享同一报告币种历史计价证明，产生 `G_F<0`、目的用途 `G>0`（若目的 U 则无 G）。旧账若不愿改该现金腿的预算归属，v4 明确拒绝，不尝试“先给虚拟 F 现金、再给真实 U 现金”而导致双计。将来若支持单笔复合状态机，须升 schema 版本并证明内部节点抵消、外部 `H` 等于原始真实资产切片；它不是本版的隐藏功能。

## 5. 价格和精度：用途划拨不拿旧成本冒充现值

报告货币在 v4 配置里**必填**，例如 `report_currency: CNY`；必须是完整根账本有效 `operating_currency` 中**恰好一个**。即使账本列了 CNY、USD、HKD、JPY，也不取第一个当默认。所有 `P/Q/E/S/G` 都用该币种；计划文件货币必须与之相同，换币种等于另做一份明确计划/报告，不改列标题。`H` 始终保留原生单位与完整 lot；不同商品不能直接求和。期末市值是可选的独立视图，缺价显示“不可用”，不把已知部分叫总市值。

**四个数不能混**：原生 `units` 用于 `H`；Beancount 成本 `weight` 用于会计/投资组配平；交易时历史价值用于 `E/S/G`；期末市场价仅用于可选市值。历史价值绝不把证券**旧成本**当作卖出时或改用途时的现值。`Income` posting 若金额为正，`S=−历史价值`，即减少此前的补充；它也可能是投资损失证据，不能从 narration 或正负号重新猜预算桶。

`E/S` 的计价**只对产生 `E/S` 贡献的切片**要求，按 posting 自身的明确证据决定，顺序固定（整条 `budget:"-"` 或全部 `outside` 的分录不产生贡献，因此不需要历史价）：

1. 若该 posting 原文写了目标报告币种的 `@@` 总价或 `@` 单价，使用其**原文精确值**；`@@` 只取一次总额，符号来自原生 units。`@ 0` 是明确零价格，不是“缺价”。若本腿同时有互相冲突的价格表达，拒绝。
2. 否则若 posting 的原生单位就是报告币种，使用原生有符号数量。
3. 否则使用已绑定该 posting 的**单一**事件专属 `PaymentAllocation`（可把一笔支付精确分到多项；分项和必须等于支付证据）；若无支付分摊，使用**单一**有来源和时点的事件报价。两种都给出但不是声明为只读交叉核对时，报 `PRICE_SOURCE_CONFLICT`，不按文件顺序选。没有则拒绝。使用 `@@` 时账本里至少一侧要写小数位：Beancount 的容差由数字写法推断，整数写法会被当作零容差，`3 USD @@ 1 CNY` 配 `1 CNY` 会直接报 `Transaction does not balance (1E-28 CNY)`（2.3.6 与 3.2.3 实测一致），把其中一侧写成 `1.00 CNY` 即可通过；本项目真实账本现有的 `@@` 写法均已带小数位。

支付腿与费用腿金额不同**不自动冲突**：例如 `Expenses 100 USD @@710 CNY`、现金支付 `−700 CNY`、折扣收入 `−10 CNY`，费用 `E=710`，另外两腿解释会计配平；不能因为只付了 700 就把本腿的 `@@710` 改成 700。若确实希望折扣冲减“已花费”，须把真实账务表达为负费用，而不是计价器暗改。

**分类切片的价值只从原 posting 的价值分配一次。** 对原生数量 `q≠0` 的一个已认证 booked posting，先按上述优先级确定其唯一有符号历史总价值 `V`。若该 posting 有一份统一的明确单价/总价，或有唯一事件报价，分类切片 `i` 的数量是 `q_i`，则精确使用 `V_i = V × q_i / q`；全部切片（**包括 `outside`**）必须满足 `Σq_i=q`、`ΣV_i=V`。之后才筛选产生 `E/S` 的切片；不能为每个桶重复读取整个 `@@` 总价，也不能把预算外份额的价值重新分给预算内。例：`Expenses 100 USD @@ 700 CNY` 被明确分为餐饮 `60 USD`、旅游 `40 USD`，则 `E` 分别为 `420 CNY`、`280 CNY`；旅游若为 `outside`，餐饮仍只计 `420 CNY`。退款 `−100 USD` 按相同有符号规则得 `−420/−280 CNY`。这只在该 posting 有**统一价格**时成立；不同实际价格被混写进一条 posting 而无逐项证明，不可按账户或叙述猜。

若使用 `PaymentAllocation` 而无统一价格，必须给每个分类切片唯一的有符号报告币种价值，所有切片（含 `outside`）的价值精确和等于同一支付证明，且不能再套用 posting 总额或另一报价。任何切片价值或支付总额无法唯一认证，都拒绝签发。`q=0` 时不得做比例除法；只有原值和全部切片值均可证明为 0 才允许全零结果，否则拒绝。原文 `@@` 如被 booking 拆 lot，须先按下文将原文总价精确分配给各 booked 子腿，再在各子腿内分配分类切片，不能跨层重复领价。

首版若 `Expenses`/`Income` posting 自身带证券成本 `{}` 或 `{{}}`，拒绝其预算计价；应把真实证券增减写在 `Assets` 腿，把费用或收入写成有明确货币价值的独立腿。否则“费用金额”会与库存成本混在一个 posting，不能由预算标签替用户选择。

`G` 只取**主动用途边界时点**的价值：报告币种现金用原生数量；外币现金、证券和其他非现金资产必须有绑定 `SliceRef/OwnershipTransfer` 的事件专属 `BoundaryValuation`。原分录上的 `@/@@` 可被这份证明**明确引用**，但绝不因带了 `@` 就自动把它当用途划拨价值；`cost/weight` 永不作为 `G` 的兜底。F→G 两端使用同一个证明和数值。`FxRate` 必须正且可逆；明确的 `ExecutionPrice=0` 可用于已证明的零价值卖出或处置，**零不等于缺失**，且不得做倒数。零价值的非现金用途划拨须另有明确的零值原因和人工确认，不从 `@ 0` 自动放行。

原文证据层以 `RawPostingRef` 保存价格 `@/@@`、成本 `{}`、总成本 `{{}}` 的原始形式与精度；官方 parser/booking 可能把 `@@` 和 `{{}}` 的总额变成有限小数单价。对 `@@` 若原始 posting 被 booking 拆成多条 lot 子腿，首版要求外部**精确分配总价**且分项和等于原文总额，否则拒绝。对 `{{总成本}}`，首版**暂不支持需要该总成本精确认证的命名用途组**，报 `UNSUPPORTED_TOTAL_COST`；不把反乘的近似值冒充原值，不误称它已被 `@@` 规则覆盖。此收窄对当前账本文本没有检出的字面 `{{` 成本写法影响较小，但未来使用时必须明确诊断。

官方 loader 的错误始终阻断。loader 接受但按原文证明恢复后仍有**真实非零会计残差**的交易，首版也拒绝签发；暂不做“人工批准 0.00135 元残差继续出数”。`@@` 造成的**纯规范化表示差**可以由原文总额证明后消去，不能掩盖真实差额。所有计算用精确十进制/有理数，最后展示才舍入；导出同时保留精确值和显示值，不经浮点中转。

## 6. 时间、期初与计划

### 6.1 cutover 与同日顺序

v4 的 `cutover` **必须是自然月第一天、当天交易开始之前**。这是最早可签发 v4 月报的月份；以前的财务历史只用于证明期初，v4 不给以前的月份签发预算报告，也不把半月 `E` 与整月 `P` 比较。例子 `2026-01-01` 只是可对撞当前历史账本的示意，不代替用户选择。请求区间有任何部分早于 cutover，拒绝该 v4 报告；任意日区间可查 `E/S/G/H`，但 `P/Q/R` 只在完整自然月或完整月份集合上有定义。

财务层的**官方 loader/booking 顺序是冻结账本事实的一部分**。同日调换两笔 FIFO 买入的源顺序，可能改变卖出成本 lot 与自动收益——这算财务输入变了，不是预算层允许自行重排。预算归属在 booked 结果上运行，只能沿与其相容的事件顺序；外部 `OwnershipTransfer` 用 `after: <Booked transaction ref>` 锚定，或用 `after: cutover` 表示锚定在 cutover（schema 见 §4.1，不使用 `at:` 这一别名）。若想卖指定 lot，优先在财务分录中明确成本/取得日/标签，重新运行 loader；预算 sidecar 的排序不能修正已经选错的 booked lot。同一原子交易先整体应用，再检查库存，不在一笔交易两条 posting 中间制造半笔透支。若同日归属事件没有足以确定“先转出还是先收入”的锚点且合法性受影响，拒绝；不按目录遍历顺序猜。

### 6.2 期初只分已有资产，不再造资产

cutover 当天交易前，由完整历史 booked 库存或经核对的权威财务起点得到每个账户、商品、完整 LotKey 的实际资产 `A0`。单独的期初归属快照必须逐坐标满足 `A0 = U0 + ΣF H0[F]` 且各份额非负；它只初始化 `H`，迁移后累计 `G=0`。cutover 前 `pad` 已在财务历史中，不能为预算再添一笔 Assets/Equity。cutover 后如仍有 pad 或插件生成资产，必须用 `GeneratedRef` 明确认领并配上真实财务对手证据；不能靠合成 posting 的 filename/lineno。没有可证明的逐 lot 期初就拒绝该持有报告，不按总商品数量猜 lot 的用途。

从 cutover 起，每个**已应用的原子事件结束后**，每个账户/商品/lot 有 `真实资产 A = U + ΣF H[F]`，并在支持域内要求 U、H、A 均非负。负库存、裸卖空和负资产账户本版明确不支持；Liabilities 仍由 Beancount 记账，不塞进 `H`。同账户的独立归属转移使 U/F 份额一减一增，真实 A 始终不变。`H_end = H_start + 区间内原生变化`，查二月末不能先丢掉一月历史。

### 6.3 月计划有两个轴，层级树不重述历史

配置是严格的版本化 YAML 数据：所有月份键必须是**加引号的 `YYYY-MM` 字符串**，金额是十进制字符串，币种与 `report_currency` 一致；禁止 YAML 日期类型、重复键、`null`、未知字段与“文字里藏月份”。`ExpensePlan` 的 `P` 与 `AllocationTarget` 的 `Q` 分开；同一个显示名可以同时存在于消费桶与用途名册，互不推导。模板按生效月份给出字段级默认值，月覆写仅替换明确列出的叶字段，其他字段继承。每个有效月的**每个活跃消费桶（该月有计划声明，或该月账本中有该桶的投影行）都必须有一个数字 P**（可以明确写 0）；每个活跃用途（同一定义）的 Q 则是一个数字或显式 `no_target`，后者仅表示不考核月划拨目标，`G/H` 仍照算。**缺失不等于 0，也不等于 `no_target`**。同月同字段两个覆写拒绝，不用“最后一个获胜”。没有交易的月份照样展开计划。旧 `2026-08-10` 和 `"2023-10 7,8,9,10月"` 只由迁移器列为待人工解释，不能截取前 7 位或从叙述猜覆盖月份。

桶树、用途树使用稳定 ID；一个节点一个父节点。父节点的 `direct` 计划与子节点计划各计一次，`subtree` 是直接节点求和；父 direct 1500、子 direct 500，父 subtree 2000。子节点 0 而由父池覆盖时，不把子节点的负 direct 余额叫独立超支。**v4 首版禁止改变已有 ID 的父节点**；想重组层级须建立新 ID 并显式迁移新计划，旧报告仍用旧树。改显示名可保留 ID 和版本化别名。这样历史聚合只有事件当时已冻结的树，不提供“按今天树重述旧月”这个第二口径。若未来需要重述，必须新 schema 并显式选择报告基准。

## 7. 易用性与支持范围：哪些可省，哪些绝不能猜

为免把全部资产腿都变成人工键入任务，v4 允许一种**显式、可审计**的账户策略：`exclusively_unassigned(account, commodity, 有效完整月份区间)`。它自动给该坐标的每条资产腿生成 `fund:"-"` 等价的**可见归属记录**，每次使用列入审计；该区间内**不允许**任何命名用途份额、指向命名用途的 inline `fund`、或侧文件用途 claim（inline `fund:"-"` 与策略等价、允许共存且不会使策略失效），一旦出现命名用途份额就整段策略失效并要求逐腿明确。它只能产生 U，不能默认推断 `储蓄`、`投资` 等命名用途。日常钱包若确实始终不承载命名用途，可用此策略省大量重复标注；混放账户及用途账户必须逐腿明确。策略也是源声明，进入快照与报告，绝非按账户名称偷偷猜。严格模式可禁用该策略。这样做降低笔数负担，但账户用途判断仍是人的输入责任，审阅界面要让它显眼。

日常 UI 不要求记住所有后缀：选择“消费类别／预算外”“未指定／已有用途内部搬移／主动划拨／有证据的用途收益”，保存前展示 `E/S/G/H` 预览、来源余额和是否配平。多用途和证券交易生成待确认的归属/组模板；**生成只是提案**，未审不得签发。只读统计当前真实账本 `[2026-01-01,2026-10-10)` 的 1923 笔交易中，有 433 笔同时含带成本资产腿与非零费用/收入对手，其中 228 笔为纯买入，66 笔成本腿另有价格。**如果这些投资资产都归命名用途，433 笔而非仅 66 笔会落入显式组审阅范围**；这是迁移候选量，不是 v4 内核已报出的错误数。应生成完整组提案并允许成批核对、局部变更重验；不能把批量确认偷换成未经人审的自动归因。原账本的任意 `comment` metadata、交易备注和原生 link 保留，不挪进预算专用字段。复杂交易需要明确证据不是 UI 失败：它们原本就不能由一条文字标签准确推出来。

首版明确拒绝或要求改写的情况：跨交易搜索同一经济组；同笔证券卖出现金直接从 F 落到 U 的自动复合解释；`{{总成本}}` 参与需要精确认证的命名用途组；无原始总价分配的 `@@` 拆 lot；无法辨认 lot 的持有变动；无明确事件价的外币/非现金 G；真实非零残差；负资产库存/卖空；未有专门证明的拆股、合并、实物分红、spin-off 等公司行为。这些拒绝是**支持域的边界**，不是悄悄算作 0。需要支持时必须增版本和测试，不允许实现者“尽量算一个”。

## 8. 签发、错误与迁移门槛

只有完整根账本 include 闭包、有效配置/计划/期初、固定 loader/插件版本和全部归属/计价证明冻结后，才能生成 `ValidatedSnapshot`。所有报告、TUI、CSV、JSON 仅从这份快照读取精确投影。筛选月份/专题不能绕过全局错误；错误时可显示源位置与**未签发**调试数据，但不得把旧报告或部分新数字装成当前有效。修改任一输入须使完整报告缓存失效并生成新快照；已有人工声明是否需要重新审批则按 §4.1 的具体依赖事实判定。异步 TUI 请求用 generation ID；多格式导出原子发布。

最低诊断协议：错误码、级别、原始 `file:line:posting_ordinal`、booked/生成子 ID、期望与实际、受影响区间、人工修法。任一必需错误阻断该快照正式签发。至少有 `LOADER_ERROR`、`INPUT_CHANGED`、`REPORT_CURRENCY_MISSING`、`REPORT_CURRENCY_INVALID`、`NAME_UNKNOWN`、`FUND_GRAMMAR`、`TRACKING_FULLWIDTH`、`CLASSIFICATION_MISSING`、`CLASSIFICATION_DOUBLE_CLAIM`、`CLASSIFICATION_VALUE_MISMATCH`、`OWNERSHIP_MISSING`、`OWNERSHIP_DOUBLE_CLAIM`、`GROUP_AMBIGUOUS`、`GROUP_EVIDENCE_MISSING`、`GROUP_EVIDENCE_OVERUSED`、`COMPOSITE_UNSUPPORTED`、`PRICE_SOURCE_CONFLICT`、`HISTORICAL_VALUE_MISSING`、`UNSUPPORTED_TOTAL_COST`、`ACCOUNTING_RESIDUAL`、`LOT_OWNERSHIP_NEGATIVE`、`ORDER_CONFLICT`、`PLAN_AMBIGUOUS`、`PLAN_MISSING`、`PLAN_DUPLICATE`、`BASELINE_MISMATCH`、`POLICY_INVALIDATED`、`PERIOD_BEFORE_CUTOVER`、`UNSUPPORTED_INVENTORY`。以下三类必须在相应输入层阻断：重复 metadata 键（`DUPLICATE_METADATA_KEY`）、保留键 `pushmeta` 注入（`META_INJECTION`）、交易级 `budget`/`fund`（`TAG_LEVEL_FORBIDDEN`）。

迁移顺序是：冻结旧账本与旧报告 → 人工选 cutover 和报告货币 → 建期初逐 lot 份额 → 把消费计划 `P` 与用途目标 `Q` 分开 → 审阅所有 cutover 后费用/收入分类与命名用途资产归属 → 为复杂交易补组/价值证明 → 在账本**副本**上做 Beancount 财务等价、库存守恒与预算对账 → 全部生产验收通过后切换。旧 398 个交易级 `budget` 不是直接可用的 v4 标签：纯资产搬移要改用途归属，多桶金额须精确拆真实 posting 或同号侧文件切片，无金额多桶要人工分配，专题 token 转 `tracking`；差额（例如旧标签金额比交易少 0.96）要明确归属或拒绝。迁移补丁有源哈希、理由、待审人、可回滚；不自动改真实账本。旧新报告不要求数字相等，但每一项差异都要能回链财务事实。当前项目的 v4 内核尚未实现，旧程序输出不可标称 v4。

## 9. 定稿判断：值得用，但不能把设计稿当验收结果

| 维度 | 判断 | 代价与限制 |
|---|---|---|
| 准确性 | **适合作为最终语义口径**：量纲、标签、组、来源、价格与拒绝规则已闭合；不能证明人的意图或财务事实本身正确 | 对证据不全的复杂交易选择拒绝，真实账本必须迁移后再签发 |
| 易操作性 | **日常场景可用**：购物/退款、普通划拨、储蓄搬家只需一两个 posting 标签；U 专属账户可用显式策略 | 证券、多用途、外币仍需审阅组/报价；现有旧账本迁移工作量大 |
| 理解性 | **可向自己解释**：消费许可、用途净划拨、实际持有三句话；`tracking` 只是筛选 | 后缀/复杂证据不应强迫用户手写 YAML，必须靠 UI 预览和诊断 |
| 实现复杂度 | **高，但被限制在有理由的边界内**：需要官方 loader、原文证据、逐 lot 所有权、侧文件 claim 和独立校验 | 首版不做通用复合状态机、任意候选图搜索、总成本恢复或债后自由现金 |

因此，v4 **可以作为最终架构定稿**，但这个结论只针对上述明确的支持域与拒绝策略；不是“任何 Beancount 交易都能自动给出预算”。若将来不愿接受某项拒绝，须新增 schema、反例测试和迁移步骤，而不能临时加一个宽松 fallback。两轮复审的规则裁决见附录；实施验收须从本文逐项建立带预期数字或明确拒绝的测试矩阵，覆盖退款、预算外分类分摊、证券组、两步撤出、引用局部重验、各种时间/计价/库存边界及所有正式输出。旧有 21+12 个语义探针和 4 个分类算术检查仅验证上游示例，不能替代 v4 编译器和真实迁移验收。**冻结的是规则，不是尚未完成的实现与易用性测试。**
