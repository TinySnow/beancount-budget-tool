# 使用指南（照着做就行）

> 这份文档替代 QUICKSTART 当"第一次上手"用。QUICKSTART 是给实现者看的，这份是给使用者看的。
> 所有命令都在本仓库根目录执行；`.venv` 是已装好的环境。

## 先理解一件事

这个工具**不是**"导入账单 → 自动出首页"。

它的流程是：

```
你的账本（.bean，事实）           你填的一张表（口径）
     │                                 │
     └──────── 工具按月核对 ───────────┘
                     ↓
        月报（每个数字都标了"已核对/待审"）
```

- **账本**记录"钱怎么动"，标签写"这笔钱算哪个用途/类别"。
- **那张表**记录"哪些账户算钱、期初的钱各属于什么用途、这个月的目标是多少"。
- **凡是你还没定的，它一律不给数**，而是列一条带 `文件:行号` 的待审项。所以"跑不出数字"通常是"表还没填完"，不是坏了。

一共就四类命令：

| 你要做 | 命令 |
|---|---|
| 第一次建表 | `beancount-budget-init` |
| 看月报 | `beancount-budget-tool` |
| 处理待审 | `beancount-budget-review`（或月报 TUI 里按 `e`） |
| 下个月 / 多月对比 | `beancount-budget-next-month`、`beancount-budget-report` |

## 2. 在你自己的账本上出第一份月报（4 步）

以你的真实账本为例（`projects/beancount/main.bean`，最后一个月是 2026-09）。

### 第 1 步：生成填写表

```bash
.venv/bin/beancount-budget-init \
  --ledger /Users/snow/homelab/projects/beancount/main.bean \
  --month 2026-09 \
  --cutover 2026-09-01 \
  --currency CNY \
  --output 2026-09
```

- **`--currency CNY` 必须给**：你的账本有多个币种，不给会报 `REPORT_CURRENCY_REQUIRED`。
- `--cutover` 是"从哪天开始按月算"：之前的所有余额只当作**期初**，不再逐笔核对。
- 输出目录不能已存在（它不会覆盖）。

跑完会生成 `2026-09/`：

| 文件 | 作用 |
|---|---|
| `setup.yaml` | **你要填的表**（唯一要改的文件） |
| `START_HERE.md` | 这张表**自己的**填写说明（比 QUICKSTART 短得多，先看它） |

你这份账本会得到：**59 个账户、72 个非零期初坐标、9 个用途**（用途是从账本里已有的 `fund` 标签自动收集的：保险/储蓄/待投资金/旅游/生活费/电子产品/自由资金/已收入资金/待支出资金）。

### 第 2 步：填 `setup.yaml`

每一行都要填，填不出来就先留着 —— 第 3 步会告诉你还差哪几行（带行号）。字段含义见第 3 节。

### 第 3 步：检查并编译

```bash
.venv/bin/beancount-budget-init --apply 2026-09/setup.yaml
```

- 没填完 → 打印 `NEEDS_REVIEW` + 每条缺什么、在 `setup.yaml` 第几行。**照行号改就行，它不会自动替你批**。
- 填完了 → `CONFIG_CREATED`，并生成 `2026-09/compiled/`（十几个侧文件 + `month.yaml`）。

### 第 4 步：看月报

```bash
.venv/bin/beancount-budget-tool --config 2026-09/compiled/month.yaml
```

如果打印的是待审清单而不是月报，进第 5 节。

## 3. `setup.yaml` 怎么填

顶层字段：

| 字段 | 怎么填 |
|---|---|
| `ledger` / `cutover` / `month` / `report_currency` | **不要动**，init 已按参数写好 |
| `defaults` | 没写标签时用的默认收入用途 / 支出用途 / 费用类别；确认后 `confirmed: true` |
| `accounts` | 每个账户一行，逐行填（下面详述） |
| `expense_targets` | 这个月每个消费类别的**上限**，填带引号的数字，如 `'2000'` |
| `allocation_targets` | 每个用途这个月的**划拨目标**，填数字；不想考核就写 `not_assessed` |
| `completeness_confirmed` | 确认"账本已记到月末、没有漏记的责任/在途付款"后填 `true` |

### `accounts` 每一行

```yaml
- account: Assets:Bank-银行:中国:工商银行:6212262318003858739
  semantics: H              # H=真实余额（可核对的钱）；K=只有申赎累计（基金/理财）
  payment_scope:
    CNY: payable            # payable=能立刻花；excluded=不能（定期/冻结）；pending=还没定
    USD: excluded
  opening:
  - commodity: CNY
    lot: CNY/no-cost
    signed_units: 136893/25      # ← 这是 5475.72，注意它是分数
    owners:                      # 期初这笔钱按用途拆开，合计必须等于 signed_units
      自由资金: '3475.72'
      生活费: '2000'
  reason: 工资卡，期初为上月结余，生活费为已划拨额度
```

四个要点：

1. **`semantics`**：能核对余额的账户（银行卡、钱包、券商现金）填 `H`；只有申赎金额、没有可信份额的（基金、理财）填 `K`。K 账户的 `payment_scope` 必须全填 `excluded`，`owners` 留空。
2. **`payment_scope`**：`payable` 才会进"能花"的钱；定期存款、冻结资金填 `excluded`。
3. **`opening.owners`**：期初余额按用途拆开。**`signed_units` 是分数**（`136893/25` = 5475.72），owners 里写小数、合计等于它；先除一下再填，`--apply` 会立刻告诉你差多少。
4. **`reason`**：写一句你凭什么这么判断。这是给未来的你看的，也是这个工具"证据优先"的地方。

### 常见填错

| 现象 | 原因 |
|---|---|
| `signed_units` 对不上 | owners 合计 ≠ signed_units（分数没换成小数） |
| K 账户报 payment_scope 错 | K 只能 `excluded` |
| `NEEDS_REVIEW` 里出现"交易级 budget 须移到对应分录" | 账本里旧写法把 `budget` 写在交易上，要改到具体 posting（工具会给 `文件:行号`） |

## 4. 月报怎么读

以公开示例 2026-10 的真实输出为例，逐节翻译：

```
v6 已审月报：2026-10（截至 2026-10-31 日末）
```
= 这个月的核对结果，截止到月末。只代表**账本记到的**月末，不代表今天的实际余额。

```
最多能花：880 CNY（生活开销消费目标差 1880；用途现金可支付 880）
```
= **还能花多少**，取两者较小的：
- 生活开销这个类别的**消费目标还剩 1880**；
- 你名下的用途资金里，**真正躺在能支付账户里的现金只有 880**。

所以"预算还有"不等于"现金还有"——这行两个数都给你，自己判断。两个口径的名字要分清：

- **实际可花** = 用途资金里真正躺在能支付账户里的现金（上面括号里的"用途现金可支付"）；
- **最多能花** = min(消费目标差, 实际可花)（行首那个数）。
  区间报表里两列都会列出来（`月末实际可花` / `月末最多能花`）。

```
其他用途可动用现金（支付范围内；已扣债务预留与未覆盖责任）
  储蓄：1100 CNY   旅游：739 CNY   电子产品：400 CNY   自由资金：2300 CNY
```
= 别的用途各有多少可动用的钱（已经扣掉被预留和欠款占用的部分）。

```
未清已记消费责任（未覆盖部分占用实际可花）
  card：120 CNY，Liabilities:Card；专用覆盖 0，未覆盖 120
```
= 信用卡还欠 120，没有专门预留来盖它，所以从"能花"里扣。

```
待报销代垫（应收原币；未到账，不计入可花现金）
  employer：待收 300 CNY ...
```
= 你替公司垫了 300，**没到账前不算你有钱**（这条特别容易让人把余额看多）。

```
消费目标（目标 − 实际；负数为超支）
  交通费用（含子类）：目标 1000，实际 700，差额 300 CNY（支出 700，退款／冲回 0）
```
= 本月预算执行情况：还剩多少 / 超了多少；括号里把"支出"和"退款冲回"分开列。

```
默认支出资金收付：生活费（实记原币）
  CNY：净流出 1000（流出 1000，流入 0）
    消费实付 700，消费退款 0，还债 0
    代垫 300，报销收回 0
```
= 你的"默认支出用途"（生活费）这个月**从哪儿出、出了多少**。注意：**刷卡在实际还款时才计入**，资产搬家/购汇/申赎不计入。

```
用途划拨（目标 Q − 实际 G；负数为超额划拨）
  储蓄：目标 700，实际 800，差额 -100 CNY
```
= 这个月"计划划给某用途多少（Q）" vs "实际划过去多少（G）"。G 只记正式划拨，消费和还款不算划拨。

```
其他 H 资产账户的用途份额（原币）
  Assets:Bank:Savings：储蓄 700 CNY
  Assets:Bank:Savings：生活费 -700 CNY     ← 这里有警告：说明该账户的生活费被透支
```
= 每一笔用途资金**具体躺在哪个账户**（验"我说的钱到底在不在那"）。

```
预算资金按用途查看（各币种与账面口径分别列示）
```
= 按用途汇总，再列分布账户。

**末尾的警告要当真**：某用途余额为负 = 这个用途已经花超了（支出导致负数是允许的，会警告；主动划拨导致负数是直接待审）。

### 状态值

| 状态 | 含义 | 能不能用 |
|---|---|---|
| `CERTIFIED_SCOPED` | 已核对（在已核对范围内） | ✅ 数字可用 |
| `NEEDS_REVIEW` | 有待审项 | ❌ 只给待审清单，不给月报数字 |
| `UNAVAILABLE` | 某个指标缺证据 | ❌ 该指标单独不可用，其它指标可能可用 |

## 5. 有待审怎么办

先分清两种待审——**处理方式完全不同**：

| 待审出现的位置 | 例子 | 怎么处理 |
|---|---|---|
| 一开头就是"导入后待审" | `FUND_GRAMMAR`（标签金额加不回分录金额）、`FUND_MIXED_SOURCE`（混合用途账户没说顺序） | **改账本**（标签写错/漏写），然后重跑 |
| 月报给出 `NEEDS_REVIEW` 待审清单 | 某笔消费算哪个类别、某笔资产用了哪份用途 | **填决定表**（下面两种方式），不用改账本 |

### 方式 A：导出填写表（推荐，可留档）

### 方式 A：导出填写表（推荐，可留档）

```bash
# 1) 导出待审表
.venv/bin/beancount-budget-review --config 2026-09/compiled/month.yaml --output review-1
```

会生成四个文件：

| 文件 | 内容 |
|---|---|
| `decisions.yaml` | **要你填的表**：每行一笔待审 |
| `choices.yaml` | 合法的类别/用途候选名（照着抄，别自己造） |
| `other-items.yaml` | 这张表**决定不了**的项（账户、期初、负债、转账协议、计价、目标）——要另外处理 |
| `START_HERE.md` | 这张表自己的填写说明 |

`decisions.yaml` 每行：

```yaml
- kind: asset_ownership      # classification=消费类别；asset_ownership=资产资金用途
  date: '2026-10-09'
  account: Assets:Mixed:A
  signed_units: '-700'
  source: .../main.bean:55
  decision: 自由资金         # ← 填名称；多用途写 '保险200，旅游900'，合计须等于分录金额；'-' 表示预算外
  reason: 这笔首次分配来自自由资金   # ← 依据
  approved: true             # ← 确认后改 true
  ref: { ... }               # ← 不要动（来源引用，工具自己不复制）
```

> 规则：`decision` 用**已登记的名称**（见 `choices.yaml`）；金额写正数、由原分录决定方向；`ref` 一个字都别改。不确定就留着 `approved: false`——可以只批一部分。

```bash
# 2) 填 decisions.yaml：填类别/用途 + 理由 + 明确批准
# 3) 保存并重跑
.venv/bin/beancount-budget-review --apply review-1/decisions.yaml
```

保存后会生成新的 `reviewed/month.yaml`，**以后都用这个新入口**（原配置不改写）。

### 方式 B：在 TUI 查看来源后修改账本／配置

```bash
.venv/bin/beancount-budget-tool --config config.yml --format tui
```

| 按键 | 作用 |
|---|---|
| `r` | 改了账本或配置后重算（重算失败会清掉旧数字） |
| `/` | 中文关键词筛选（用途/类别/账户/原因码/金额） |
| `↑↓` / `j k` | 滚动一行或选择一笔 |
| `空格` / `PgDn` | 向下翻整页 |
| `b` / `PgUp` | 向上翻整页；Windows 不方便按翻页键时可直接用字母键 |
| `g/G` / `Home/End` | 到首尾 |
| `o` / `O` | 交易列表、普通科目流水和报错前流水切换正序／倒序；默认最新在上，切换后回到顶部 |
| `Enter` | 看选中待审的完整原因、文件行号、来源引用 |
| `t` | 在"月报"和"待审列表"之间切换 |
| `e` | 查看待审来源与修改指引；用户修改账本／两份 YAML 后按 `r` 重算 |
| `a` | 签发后看当月逐笔交易；`Enter` 看每笔的分录/类别/用途/责任 |
| `h` | 查看科目用途历史；用途透支报错时查看失败交易前的诊断流水 |
| `?` 帮助 / `q` 退出 / `Esc` 关闭 |

> 排序只改变 TUI 展示；每笔余额仍是该笔交易后的余额，期初／期末不变。排序偏好仅在本次会话保留，不增加配置字段、不读写 reviews；CLI 和导出仍保持原有正序。报错前流水始终只是诊断，不能据此签发月报。

## 6. 下个月、多月对比

### 准备下一月

```bash
.venv/bin/beancount-budget-next-month --config 2026-09/compiled/month.yaml --output 2026-10
```

生成 `2026-10/next-month.yaml`（改这个月的目标和账户变化，**cutover 保持不变**）+ `preparation.yaml` + `START_HERE.md`。填完：

```bash
.venv/bin/beancount-budget-next-month --apply 2026-10/next-month.yaml
```

月度资料完整性的确认（月末有没有漏记的责任/付款）——它要**单独用**，不能和 `--config` 同时给，且必须给新的 `--output` 目录：

```bash
.venv/bin/beancount-budget-next-month \
  --confirm-completeness 2026-09/compiled/month.yaml \
  --reason "9 月末流水已全部入账，没有未记的责任或在途付款" \
  --output 2026-09/completeness
```

### 比较几个月 / 导出 CSV

```bash
.venv/bin/beancount-budget-report \
  --config 2026-09/compiled/month.yaml \
  --config 2026-10/compiled/month.yaml \
  --format csv --output q3-q4.csv
```

- `--config` 可以给多个，**不能缺月**；
- `--from 2026-09 --through 2026-12` 限定区间；
- CSV 带 UTF-8 BOM，Windows 打开中文不乱码；
- 区间报告里"期末最多能花"与逐月余额**不相加**（避免重复计入），消费目标与 Q−G 逐月比较。

## 7. 术语表

| 词 | 人话 |
|---|---|
| H 账户 / K 账户 | H = 能核对余额的真账户；K = 只有申赎累计的基金/理财 |
| 用途（fund） | 这笔钱属于哪个预算科目（生活费、旅游…） |
| 类别（budget） | 这笔消费算哪个消费类别（交通、家电…） |
| 默认支出用途 / 默认收入用途 | 没写标签时的兜底用途 |
| 代垫 | 你替别人垫付、还没收回的钱（到账前不算可花） |
| 预留 | 专门圈出来还某笔债的钱（不从"能花"里重复扣） |
| Q / G | 划拨目标 / 实际划拨 |
| 认证状态 | 每个指标单独标"已核对/待审/不可用" |
| 快照不匹配（`*_SNAPSHOT_MISMATCH`） | 配置/证据和当前账本不是同一版本（账本改了就要重新审） |

## 8. 排错

| 报错 | 怎么办 |
|---|---|
| `REPORT_CURRENCY_REQUIRED` | 加 `--currency CNY`（多币种账本必须显式指定） |
| `NEEDS_REVIEW` + 一堆行号 | 照行号改 `setup.yaml`；`--apply` 再跑一次 |
| `ACTUAL_SNAPSHOT_MISMATCH` / `K_BOOK_SNAPSHOT_MISMATCH` | 账本改过之后，旧的审阅快照失效：重新跑 init / review，不要手改侧文件 |
| 输出目录已存在 / 不覆盖 | 换一个新的 `--output` 目录 |
| 月报只有待审清单没有数字 | 正常：**没核对完就不给数字**，处理待审后重跑 |
| TUI 重算失败并清空数字 | 正常：它不会留着旧数字骗你；改完按 `r` |

## 10. 逐月清理历史账本（从旧账重建 v6）

**可以，而且这就是工具设计的主线。** 每月只处理一个月，签发了再走下一月。

### 一次性准备：生成"审阅副本"

不要直接在原账本上改。先生成一份独立副本：

```bash
.venv/bin/python -m beancount_budget_tool.tools.v6_make_review_copy \
  --ledger /Users/snow/homelab/projects/beancount/main.bean \
  --destination migration
```

它只做一件事：把交易级的旧 `budget` / `fund` 元数据**改名**成 `legacy_budget` / `legacy_fund`
（保留成"提示"，不再当作错误），不改任何金额、账户、日期。你这份账本会改名 **398 处**。

所以：**旧标签不需要逐笔手改**。想细分的地方再补行内标签，普通收支由"默认类别"覆盖。

### 每月循环（以 2023-07 为例）

```bash
# ① 改前留 checkpoint（改坏了能退回来）
cp -r migration checkpoints/2023-07-before

# ② 单月复审：先看这个月还差什么（只报这一个月，未来月份不挡路）
.venv/bin/beancount-budget-review-month \
  --before checkpoints/2023-07-before/main.bean \
  --after  migration/main.bean \
  --month 2023-07 --cutover 2023-07-01

# ③ 首月建配置（之后每月用 next-month）
.venv/bin/beancount-budget-init --ledger migration/main.bean \
  --month 2023-07 --cutover 2023-07-01 --currency CNY --output budget/2023-07
#    填 budget/2023-07/setup.yaml（账户语义/支付范围/期初用途/目标）后：
.venv/bin/beancount-budget-init --apply budget/2023-07/setup.yaml

# ④ 再加 --config 跑同一条命令 → 出这个月的月报
.venv/bin/beancount-budget-review-month \
  --before checkpoints/2023-07-before/main.bean \
  --after  migration/main.bean \
  --month 2023-07 --cutover 2023-07-01 \
  --config budget/2023-07/compiled/month.yaml
```

看到 `单月复审 2023-07：CERTIFIED_SCOPED` + 月报 = **这个月签发了**。

### 下一个月

```bash
# 从上月已签配置准备下月目标
.venv/bin/beancount-budget-next-month --config budget/2023-07/compiled/month.yaml --output budget/2023-08
#    改 budget/2023-08/next-month.yaml 的目标后：
.venv/bin/beancount-budget-next-month --apply budget/2023-08/next-month.yaml
# 然后重复 ②④
```

### 这套流程的几个保证

| 保证 | 怎么体现 |
|---|---|
| 只动目标月 | 输出 `账本改动范围：仅目标月交易块`，动别的月会报错 |
| 财务事实不变 | 输出 `booked 财务事实：未变`；真要改错账才加 `--allow-financial-corrections`，它会列出改前/改后分录 |
| 未来月份不挡路 | **月报只重放截至该月末的指令**：2023-08 及以后所有旧标签都还没清理，2023-07 照样能签发 |
| 不要求逐笔补标签 | 首轮盘点的"未写 budget 的 31 条"不是待办清单；已审默认类别覆盖普通分录 |
| 原账本只读 | 改的是 `migration/` 副本；原账本一行不动 |

### 边改边看

```bash
# 改一个月的账本，保存就自动重跑（Ctrl+C 停止）
... --month 2023-07 --cutover 2023-07-01 --watch
```

### 两个坑

1. **`--before` / `--after` 必须是两个独立目录的完整副本**，不能是同一个文件或同目录里两个 main.bean
   （会报 `MIGRATION_SAME_INPUT` / `MIGRATION_SOURCE_LAYOUT`）。每月改前复制一份目录即可。
2. **不要攒着改**：命令会校验"改动限于目标月"，一次改三个月会被拒。

### 工作量大致什么样

- **首月最重**：账户语义/支付范围（你账本 5 户）+ 期初用途拆分 + 默认类别 + 本月目标。
- **之后每月很轻**：上月配置 `next-month` 改目标 → 补当月少量标签（想细分才补）→ 处理本月待审 → 签发。
- **历史目标从哪来**：`projects/beancount/budget/budgets.yml` 里有 2023 年起的月度计划；
  注意其中 `"2023-10 7,8,9,10月"` 这种叙述式月份键需要你自己解释成具体月份。

> 一句话：**这套工具就是为"逐月清理旧账"设计的**。你要的正是它的主线用法。

## 11. 配置全景：填什么、哪些必填、几张表

### 你只填 3 类表，其余是编译产物

```
setup.yaml（首月 1 张）──┐
next-month.yaml（每月 1 张）─┼─→ compiled/ 里 14 个配置文件（不用手填）
decisions.yaml（有异常才 1 张）┘
```

`compiled/` 里的 14 个文件：`month.yaml`（主）+ `accounts` `opening` `ownership` `classifications`
`obligations` `expense_plans` `purpose_plans` `purpose_pools` `h_transfers` `h_fx` `k_events`
（以上 12 个在配置里是**必须有**的）+ `completeness` `benefit_groups` `debt_coverage` `debt_settlements`（可选）。
它们都在，但内容由你填的表编译而来。

### 能配置什么

| 层次 | 配什么 | 在哪儿填 | 频率 |
|---|---|---|---|
| **一次性** | 账户是 H（能核对）还是 K（基金申赎）；每个币种能不能花（payable/excluded）；期初钱按用途怎么拆；默认收入/支出用途；默认消费类别 | `setup.yaml` | 首月一次；**新账户首次出现**时补 |
| **每月** | 各类别消费上限（含子类）、各用途划拨目标、新账户/新币种定性、目标确认、资料完整性确认 | `next-month.yaml` | 每月 |
| **按需**（有异常才出现） | 每笔消费的类别、每笔资产的用途归属 | `decisions.yaml` | 有 `NEEDS_REVIEW` 时 |
| **按需**（特殊事项，直接改侧文件） | 负债责任/期初未结清、资产转账协议、外币计价、基金申赎事件、专项卡债覆盖、资金池、福利组 | `obligations` `h_transfers` `h_fx` `k_events` `purpose_pools` `benefit_groups` 等 | 账本里出现对应东西时 |
| **全局** | 账本路径、cutover、报告货币 | `month.yaml` | 首月定，之后不动 |

### 必填项

**硬必填（不给就跑不了）**

| 表 | 必填 |
|---|---|
| `setup.yaml` | `defaults.confirmed: true`；每个账户 `semantics` + `payment_scope`（每币种）+ `reason`；H 账户期初 `owners` 合计 = `signed_units`；`expense_targets` 每个类别一个数；`allocation_targets` 每个用途一个数或 `not_assessed`；`completeness_confirmed: true` |
| `next-month.yaml` | 三个目标核对后 `targets_confirmed: true`；`completeness_confirmed: true` + `completeness_reason` |
| `decisions.yaml` | 每行 `decision` + `reason` + `approved: true`（不批就保持 false，继续待审） |

**条件必填（账本里有那类东西才必须填）**

| 账本里出现了 | 必须补 |
|---|---|
| 新账户 / 新币种 | 下月表的 `account_changes` 定性 |
| 有余额的负债账户 | `obligations` 里声明责任类型/归属 |
| 外币腿或外币负债 | `h_fx` 计价（否则该指标「不可用」） |
| 基金/理财申赎 | `k_events` 事件 |
| 跨账户资产转账 | `h_transfers` 协议 |
| 期初有尚未结清的债务/代垫 | `obligations` 的 `opening` |

**可选**：资金池（`purpose_pools`）、福利组（`benefit_groups`）、专项卡债覆盖（`debt_coverage`/`debt_settlements`）。

### 一共要填几张表

| 场景 | 表数 |
|---|---|
| 第一次跑起来（首月） | **1 张**：`setup.yaml` |
| 之后每个新月份 | **1 张**：`next-month.yaml`（有分类/用途待审再 +1 张 `decisions.yaml`） |
| 清理全部历史（2023-07～2026-09，39 个月） | **39 张**：首月 1 张 + 之后 38 张月表（待审表另计） |

> 注意：首月表会一次生成 14 个配置文件，但**你不需要碰它们**；只有上面"按需/特殊事项"里列到的才要手工编辑。

### 迁移 vs 新账本：同一套流程

| | 迁移旧账 | 每月新记账 |
|---|---|---|
| 首月建表（账户/期初/默认/目标） | 要（cutover 设在要开始的那个月） | 要（第一次用时） |
| 每月 `next-month.yaml` | 要（历史每个月都要做一次，按时间顺序） | 要（每月） |
| `decisions.yaml` | 要（旧账的歧义多） | 偶尔（异常交易） |
| 特殊事项侧文件 | 要（旧账的转账/负债/基金多） | 出现时才要 |
| 额外动作 | 审阅副本、每月 checkpoint、`--before/--after` 单月复审 | 导入后先看待审清单 |

**结论**：迁移不是另一套流程，而是"把每月的增量流程在历史上重放一遍"。一次性配置只做一次；
新账本每月也要做的是「月表 + 待审决定 + 完整性确认」。

## 给你的建议路线

1. **今天**：跑第 1 节的三个月 demo，看懂第 4 节的月报。这一步只要 5 分钟。
2. **然后**：从 **2026-09**（你最后一个月）开始建第一份表——**不要**从 2023-07 那条全历史迁移开始，那是几十个账户 × 几十个月的工作量，先拿到一份能签发的月报，再决定要不要补历史。
3. 填表时**先只填 H/K 和 payment_scope**（这两个填完 `--apply` 的待审会少一大半），再处理期初 owners，最后填目标。
4. 每月流程固定下来就是：`next-month` → 改目标 → `apply` → `月报` → 有 `NEEDS_REVIEW` 就 `review` 填掉 → 签发。
