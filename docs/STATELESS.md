# 账本与两份YAML是完整的运行输入

本阶段落实用户在2026-10-28补充的要求：程序不应在任何日常运行阶段读取、创建或更新`reviews.json.gz`。已完成的0a8903c是行为等价的历史基线；其中隐藏审阅状态兼容不属于当前产品合同。

## 日常操作

只维护自己的Beancount账本、`config.yml`和`budgets.yml`。程序根据这些明确输入计算：全部可证明时签发；缺少配置、来源或存在歧义时列待审，不能由按键批准。

- 分录用途：资产posting的`fund`；费用/收入及负债责任posting的`budget`；专题`tracking`。
- 账户性质、可支付范围、期初用途、默认规则、负债规则：`config.yml`现有字段。
- 消费/用途目标、真实工资日与额度：`budgets.yml`现有字段。
- 月末资料完整性：只在该月份明确设置`completeness_confirmed: true`；未核对时留空或设为`false`，不能放进跨月默认层。

```yaml
# budgets.yml 的片段
schema: 1
months:
  "2024-09":
    completeness_confirmed: true
    expense_targets:
      生活开销: "3000"
```

`true`表示用户在可见YAML中作出了该月声明，不是程序根据账本笔数、缓存或旧批准推断。之后的查询总会重新校验当前账本。需要撤回时改为`false`；下一月需要独立配置。

TUI的`e`只显示所选待审项的来源及如何修改；`f`只显示月末YAML填写指引。它们不收集批准、不保存理由、不改账本或配置。编辑器保存后按`r`或等待watch重算。取消、退出、待审、报错及导出均不会生成审阅状态。

## 复杂协议也是显式配置

隐藏状态曾保存的复杂依据不能默默丢失，也不能因此继续读取旧文件。确实需要逐来源声明时，直接写在两份YAML中的`declarations`。这是可检查、可编辑的输入值，不能填写某个外部审批文件路径。

共享声明在`config.yml.declarations`：

| 字段 | 内容与验证 |
|---|---|
| `accounts` | 只接受`credit_card_whitelist`、`same_day_settlements`；普通账户属性仍使用`accounts`/`account_groups` |
| `ownership` | `owners`、`claims`、`transfer_orders`；普通交易优先填写fund，不能声明不存在或过期的来源 |
| `classifications` | `categories`、`classifications`；普通交易优先填写budget，金额和类别仍严格核对 |
| `obligations` | 明确的期初责任、消费/还款/代垫及来源关联；不按同额或日期猜测匹配 |
| `benefit_groups` | 本金、退款与收益的明确来源组，防止重复计入 |
| `purpose_pools` | 证券池的范围、保护本金与剩余用途；成本、市值和现金不混合 |
| `h_transfers`、`k_events`、`h_fx` | 原来支持的转账/申赎/购汇协议，保留原文价格和精确守恒门禁 |

逐月声明在`budgets.yml.months.<月份>.declarations`：

| 字段 | 内容与验证 |
|---|---|
| `completeness` | 完整的该月截止日声明，可明确保留理由；不会自动套用到其他月份 |
| `debt_coverage` | 该日责任与专用支付资源的明确分配；资源不能重复使用 |
| `debt_settlements` | 该日外币责任锁定清偿额或明确未锁定；不使用未来付款价代替 |

协议值沿用各财务域的严格声明格式，包括需要的schema/cutover/来源身份/loader版本、日期及金额字段。最常见的情况不需要填写这些底层字段；使用账本标签和现有规则即可。缺少协议时保留待审或明确的实现缺口，不自动构造一项批准。

显式`completeness_confirmed`优先于该月`declarations.completeness`：`false`明确撤回；`true`采用当前YAML中的简单声明；省略时才使用该月明确的完整声明。不存在隐藏状态回落。

`ownership`/`classifications`的来源声明仍绑定原始交易内容、occurrence、posting/booked ordinal、lot和fact摘要。修改所绑定的交易后必须重新明确，不能靠旧哈希或理由继续认领。交易外空行等无关变化不会伪造新身份。复杂负债、同日结算和证券等财务协议没有因取消批准UI而削弱。

## 旧版本数据

现有`.budget-state`原样保留：当前程序不读取、监听、导入、重写或删除它。旧文件损坏、内容变化、存在或不存在均不改变新查询的金额或认证。以前仅靠旧隐藏批准才能签发的月份，现在若在账本/两份YAML中没有明确依据，就应当待审。

`state`、`clean`、`review`等旧保存命令明确返回退役提示。旧`beancount-budget-state`安装入口已移除，独立状态存储模块不再发布。最终可执行包也不包含旧审批/保存适配模块。

用户显式提供旧多文件`month.yaml`时，可以使用`configure --from-config`把其明确内容写到新建的两份YAML，目标目录不能已存在，旧文件不会被覆盖。该操作不搜索或导入`reviews.json.gz`。复杂依据成为可见`declarations`，月度依据归入对应月份；正常报表计算从不调用迁移。

## 验证边界

新合同测试覆盖干净目录零隐藏状态、损坏旧状态不被打开、旧批准不能认证缺少公开声明的月份、TUI不收集批准也不写文件、显式YAML变更后认证、来源claim失效及旧保存命令退役。原来的责任容量、同日结算、费用/外币、future cutoff等财务断言保留；只有被用户取消的“键盘批准并持久保存”行为测试退役。

运行生成的schema6文档只是内存/系统临时适配，不是用户需要维护的第三份配置。证据摘要继续按与该平台物理YAML写入一致的字节生成，LF/CRLF合同不变。新版本验证和平台CI结果以当前无状态提交为准，不使用历史1091项stateful结果替代。

本地当前验收：1078项完整测试通过（31.96秒）。同一路径的隔离账本在2023-07至2026-09的39个月完整JSON、待审和错误与0a8903c相同；14个月及区间共15份JSON、公开虚拟验收6份输出逐字节相同，859个账本文件清单与摘要不变。该账本原本没有隐藏批准，旧文件忽略及缺少公开声明转待审另外由专门用例验证，不能用结果相同推断旧状态仍会迁入。

本机macOS arm64实际单文件包已验证：e/f只显示指引且输入文件不变；编辑budgets.yml后watch由待审转认证；失败页h保留未签发的诊断语义，组合交易详情和watch重算保持。包内归档不含state_store及旧批准/保存适配模块。远程Windows/Linux测试与三平台包验收待本次提交推送后记录，不能沿用旧提交的绿色状态。
