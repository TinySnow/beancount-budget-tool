# v6 已审月报：一条命令查看已认证结果

若希望月报首页给出受生活费预算约束的「最多能花」，在消费目标文件顶层指定 `spendable_cap_category_id`，并为该类别声明本月显式 `expense_subtree_targets`。首页取**已审用途现金可支付金额**与**该类别消费目标差**的较小值；两项原值在 JSON 中分别保留。上限类别可由使用者选择，不在公共代码里固定为「生活费」。未配置上限时只显示用途现金可支付金额，不称作「最多能花」；配置了上限但本月缺目标时列入指标待审。

```yaml
schema: 6
report_currency: CNY
spendable_cap_category_id: living
months:
  "2026-09":
    expense_subtree_targets:
      living: "2000"
```

首次给导入流水添加 `budget`／`fund` 标签，请先看 [QUICKSTART](../QUICKSTART.md)。

本页适用于**已有 v6 已审配置**的使用者。首次接入可先按 [QUICKSTART 的集中填写表](../QUICKSTART.md#首次建立配置先填一张表)运行 `beancount-budget-init`；确认首轮决定后，它会编译本页所需的侧文件。公开的 `examples/v6/first-month-setup.yaml` 可运行完整虚拟月报。下面的 2026 年 9 月配置属于维护者本地私人账本，不随公开仓库发布。

逐月审核时，可以共用账户、分类、资产用途、简单转账／购汇／K 申赎、已记责任和证券收入组的审阅文件。新增下月决定后，重跑旧月只计算旧月截止日以前的交易；未来来源仍须有效，两腿事件仍须绑定同笔交易的完整对手。新账户及新币种的支付范围只在它们实际出现的月份参与审核。改过已认领交易后仍须重审失效引用。

完整性声明 `completeness`、专项卡债覆盖 `debt_coverage` 和外币清偿报价 `debt_settlements` 绑定报告日，需在各月配置中引用该月适用的文件；共用交易审阅文件不代表这三类时点资料也能共用。

准备紧接的下一月可用 `beancount-budget-next-month --config 上月最新配置 --output 新目录`，核对生成的 `next-month.yaml` 后用 `--apply` 编译。原 cutover 与共享来源认领保持，目标提议需确认，新账户／币种只补新增决定；旧报告日资料不自动复用。若先审交易，后来才确认月末完整性，用 `--confirm-completeness 本月最新配置 --reason 核对依据 --output 新目录` 保留本月审阅进展；该声明不能替代责任、计价或其他指标审计。步骤见 [QUICKSTART 的下一月准备](../QUICKSTART.md#先准备下一月)。

遇到尚未认领的分类或 H 资产用途，可用 `beancount-budget-review --config month.yaml --output review-month` 导出交易填写表，填名称、理由并明确批准后，用 `--apply review-month/decisions.yaml` 保存。工具生成新的分类／归属文件和 `reviewed/month.yaml`，保留原有已审决定并重跑月报；之后以新配置继续。金额拆分、来源过期与重复认领仍按正式审计校验。详细步骤见 [QUICKSTART 的交易待审填写表](../QUICKSTART.md#待审的类别用途只填决定不复制来源引用)。该入口不自动认领负债、K 事件、计价或计划。

当前入口先检查本月来源待审项，再审计 **实际可花、消费目标差、用途划拨目标差、资产账户用途份额、证券资金池保护额与 `tracking` 专题**。有来源待审项时显示交易清单和账本行号；来源通过但某个指标未认证时显示指标及原因；全部通过后显示已审月报。消费类别保留支出、退款／冲回与净额；专题只汇总费用分录的原币金额，不改变预算类别或资金用途。同一费用可属于多个专题，因此专题间不能相加。账户用途按 H 资产的原币余额显示；非证券池账户中任一具名用途份额为负，会在文字报表警告并在 JSON 单列；证券池另按账面成本展示，K 与证券市值不并入这份余额。配置了收入、支出双默认用途时，实际可花以默认支出用途的可支付现金为基础；收入默认用途须显式划入后才可消费。已审报告货币卡债须与负债账户余额逐项相符；默认支出用途责任未覆盖的全额占用实际可花，专项责任可通过已审专用现金覆盖，剩余缺口仍占用实际可花。月报列出责任未偿额、专用覆盖与未覆盖部分，以及支付范围内专项用途的可动用现金。外币债务可用已审锁定账单清偿额；缺决定时待审，明确未锁定的兑换路径仍为实现缺口。它目前只支持完整自然月，不是今天的实时首页，也不签发计划兑现后可花或完整历史净费用。

K 账面累计账户单列期初、cutover 后变动、期末，以及逐账户、逐用途的**已审申赎净变动**。只有 K 腿用途与同笔真实现金腿精确匹配的简单事件才进入已审切片；未审事件另列数量与账面变动。切片不含 cutover 前未知的用途分布，也不表示基金份额、市值或可赎回金额；不与真实 H 库存相加。

月报现在也提供「预算资金按用途查看」：列出归属配置里登记的每个用途，标出默认收入／支出用途，分别显示它在各账户的原币 H 余额、证券池账面成本和 K 已审申赎净变动。没有余额的已登记用途仍会显示；某账户用途余额为负时，即使该用途的跨账户合计不为负，也保留警告与账户分布。不同币种不折算合计，三种口径各自汇总；`fund: "-"` 的持有另列为预算外。JSON 对应字段为 `report.purpose_balances`，TUI 与文本显示相同内容。

### 默认支出资金收付

配置了默认支出用途后，月报单列这份资金实际付出的消费、收到的消费退款、个人债务还款、单位代垫及报销收回，显示各币种的净流出和账户分布。JSON 对应 `report.default_outflows`，每条事件保留资产分录、同笔对手及账本行号。

按**资产腿的资金用途**统计：一笔 50 元付款由生活费 20、储蓄 30 承担时，这里只计生活费 20。`budget` 费用类别与 `fund` 资金用途各自计算；预算外费用类别仍可动用具名资金，`fund: "-"` 则排除在具名用途汇总之外。信用卡刷卡时尚未支付资产，在实际还款月才计入这份资金收付；消费类别仍在原消费月统计。资产搬移、虚拟调拨、购汇和 K 申赎排除。只有净收入资产入账、手续费已从到账金额抵扣时，不虚构另一条资产扣款。

已审证券池只含储蓄、投资等其他用途时，沿用池级用途集合证明它不涉及默认支出资金，不要求重新逐 lot 标注。若池内分录显式写了默认用途、却与池级用途集合冲突，保留待审。费用和退款在同笔抵扣且只有一条资产净额时，此处按该资产净额记录收付，费用分类仍保留原分录明细。

例如生活费实际支付消费 30、收到退款 5、还卡 40、代垫 50、收到报销 30，本项流出 120、流入 35、净流出 85。未报销余额另外列为应收。此项只描述资金流向，实际可花、消费目标差及用途 G 按原有口径计算。退款可使净流出为负。

外币还款保留实记原币，如 21.76 USD；用于购汇的人民币资产转移不会在这里再次计入，也不把两种币种相加。该原币资金汇总与消费目标使用的已审人民币结算成本分开。当前支持唯一 H 资产腿对应同币费用（含净结算费用束），及已审简单还款／代垫协议；无法确定流向的复合事件明确标记程序实现缺口，完整月报保持阻断，不把已知部分当作全月总额。

### 混合用途账户：可选转出顺序

同一 H 账户同时放投资和储蓄，省略 `fund` 的部分转账可以在 `ownership` 文件顶层声明顺序。下面是**私人规则示例**，用途 ID 须在该文件的 `owners` 中登记；公共默认不会启用它：

```yaml
transfer_orders:
  - account: Assets:Broker:Cash
    commodity: CNY
    owner_ids: [investment, savings]
    reason: 已确认这户人民币资金转出时先用投资，再用储蓄
```

例如交易前投资 100、储蓄 300，转出 150 时自动继承投资 100、储蓄 50，转入腿省略 `fund` 时也沿用这份拆分；纯搬移的 G 为零。转出腿显式写 `fund: "储蓄"` 时，以标签为准。规则只作用于所列账户和币种的简单同币 H 转账，需要同时配置双默认用途以启用交易前库存重放。它不选择消费付款用途、不推断 K 申赎或证券成本 lot，也不允许主动划拨透支。未列入顺序的用途不会被自动使用；期初未知或所列用途余额不足时仍待审。不配顺序时，混合用途的部分转账继续待审。

### 证券池亏损：可选负数余款

证券池原有默认仍要求账面成本全程足以覆盖保护本金。若采用“储蓄名义本金固定、亏损由投资承担”的私人规则，可在对应 `purpose_pools.pools` 项中加入：

```yaml
remainder_policy: allow_negative
```

例如池内账面成本 4,000、名义储蓄本金 3,000，发生 1,500 已实现亏损后，显示储蓄 3,000、投资 −500，并警告本金存在 500 账面缺口。不是声称还能取回 3,000；市场报价下跌本身不会改写账面成本。期初已有缺口也按这份显式决定展示。缺口补足后仍保留本期间的最大缺口记录。

按账户展示仍先依 `reserve_order` 分布本金；当整个池的账面成本已不足，未覆盖的名义本金放在顺序中的第一户，该户余款为负。每户两项之和仍精确等于其账面成本，整个池两项合计也守恒。JSON 状态为 `CERTIFIED_NOMINAL_PURPOSE_BALANCES`，当前缺口为 `principal_book_shortfall`，cutover 以来最大缺口为 `maximum_principal_book_shortfall`；按用途视图提供 `has_negative_pool_position`，文本与 TUI 显示警告。亏损不会变成现金或新划拨 G；真实库存仍不得为负，向池外主动转出不得制造或扩大缺口。该配置不代替本金正式调出时的边界审阅，也不自动改变固定本金数额。

## 2026 年 9 月隔离副本配置示例

此私人配置的旧审阅文件绑定 Beancount 2.3.6；项目当前依赖 3.2.3。配置指向的隔离副本也比部分审阅文件所用的副本更新。直接运行会先因版本不一致停在分类校验；仅改版本号仍会遇到过期引用。下面的命令展示入口用法，须逐份复核审阅来源后才能用于这份账本。

可先用只读命令盘点配置中所有侧文件的过期引用及 loader 差异：

```bash
beancount-budget-review-refs --config path/to/reviewed-month.yaml
```

它列出审阅文件中的位置、当前账本里同文件同 booked 事实的**候选**来源，以及行内 `fund`／`budget` 与侧文件的重复认领；候选不能自动替换原批准。跨 loader 时先用 `beancount_budget_tool.tools.v6_compare_bookings` 分别生成两版 booked 快照并比较，再逐份重审受影响的引用、用途名册及金额，最后运行正式月报。原审 `ledger_snapshot` 是历史审阅凭据，不应为消除差异直接改成当前哈希。引用盘点本身不签发任何预算数字。

用途净划拨审计会接受已审的简单信用卡还款及单位代垫／报销，核对责任事件与 H 资产腿来源，并将它们记为 **G=0 的责任结算**。仅有用途标签而未审责任时仍待审。无需月度划拨目标的用途可在用途计划中显式写 `not_assessed`；文本月报仍显示它当月的实际净划拨，不能把未审实际划拨藏在“不考核”后面。

在项目根目录，使用已安装 Beancount 的 Python：

```bash
PYTHONPATH=src python -m beancount_budget_tool.v6.monthly_report \
  --config fixtures/private-ledger/reviews/v6-monthly-report-2026-09.yaml
```

需要待审来源和状态的结构化结果时加 `--format json`。来源或任一指标未通过时，JSON 的 `report` 是 `null`，`review_items` 汇总具体阻断原因与文件行号；原有 `review_queue`、`pending_metrics` 仍保留。指标待审项包含受影响的 `metrics`，同一来源原因不会因同时影响“实际可花”和“最多能花”而重复列出。通过全部审计后才提供报表。私有配置里的路径相对于配置文件所在目录；账本原件没有被改写。自己的月份须提供同样的已审输入，并把 `month` 改为目标月份；报表日自动取该月末。没有该日人工完整性声明时可省略 `completeness`，入口会报告实际可花待审。

数据或审阅决定缺失时，状态为 `NEEDS_REVIEW`，清单解释需要核对什么；外币消费缺计价会定位到费用分录，未清责任会定位到相关负债分录，缺目标会指出类别／用途和计划文件。嵌套计划金额、未知类别／用途 ID 和完整性声明字段错误也有 YAML 行号。找不到尚未填写的字段时，位置指向最近的已有配置层。

当前入口尚未实现的计算会明确标为“程序实现缺口”，状态为 `IMPLEMENTATION_BLOCKED`，对应待办的 `reason_kind` 是 `implementation_limit`。这包括未锁定外币责任的报告日兑换路径计价、非消费借款和复合期初责任及不符合现有协议的复合事件。它们需要继续开发，不能靠改标签或人工批准消除。有实现缺口时仍列出同时发现的数据待审项。

完整性声明按指定月末使用，不要求账本哈希保持不变；旧声明中的 `ledger_snapshot` 和 `as_of_booked_fingerprint` 可留作历史记录，也可删除。补记旧月交易后，程序会重新计算现金与已入账责任；新交易缺用途或责任认领时，月报仍会列为待审。完整性声明只涉及其所写的月末，不把历史报表变成今天余额。

配置为 schema 6 YAML，字段如下。此例展示字段，路径须按自己的审阅文件填写：

```yaml
schema: 6
ledger: ../review-copy/main.bean
cutover: '2026-09-01'
month: '2026-09'
report_currency: CNY
accounts: accounts.yaml
opening: opening.yaml
ownership: ownership.yaml
obligations: obligations.yaml
completeness: completeness.yaml # 可省略；只适用于声明的月末
debt_coverage: debt-coverage.yaml # 可选；专项未偿卡债的报告日覆盖决定
debt_settlements: debt-settlements.yaml # 可选；外币债务的报告日锁定账单
classifications: classifications.yaml
benefit_groups: benefits.yaml # 可省略；复杂收益未审时相关指标会待审
expense_plans: expense-plans.yaml
purpose_plans: purpose-plans.yaml
h_transfers: h-transfers.yaml
k_events: k-events.yaml
h_fx: h-fx.yaml
purpose_pools: purpose-pools.yaml
```

## 从历史月份开始：切换前还没结清的债务或代垫

例如 cutover 为 9 月 1 日，8 月刷卡 500 元、已还 200 元：只把 **9 月 1 日交易前仍欠的 300 元**结转为期初责任。8 月消费不会进入 9 月费用，9 月还款继续扣减同一责任。未收回的单位代垫同样只结转尚未报销的金额，不提前增加可花现金。

在现有 `obligations` 文件中补可选的 `opening` 列表，不新增账本交易。先运行月报的 `--format json`：`LIABILITY_OPENING_PENDING` 项会列出账面余额及 `source_candidates`，从中选择真正尚未结清责任的原始来源，把完整 `liability_ref` 复制到期初项；候选并非自动批准。金额需要你按账单确认，程序不能从往来净余额猜出各笔剩余。以下只展示新增列表，原文件的 schema、cutover、loader_version、owners、events 等字段仍保留：

```yaml
opening:
  - kind: consumer_debt
    obligation_id: old-card
    owner_id: living # 已登记的资金用途 ID
    liability_ref: {} # 替换为 cutover 前消费或已有 Equity 结转的完整来源
    remaining_native: '300' # 原币未偿额，始终为正数
    reason: '8 月消费 500，切换前已还 200，余款由生活费承担'
  - kind: advance_receivable
    clearing_id: old-advance
    liability_ref: {} # 替换为 cutover 前代垫或已有 Equity 结转的完整来源
    remaining_native: '300'
    reason: '切换前仍有 300 元单位代垫待报销'
```

每个账户／币种／lot 必须满足“期初应收 − 期初债务 = cutover 前 booked 余额”。同一坐标可列多个独立 ID；若应收与债务恰好相抵为零，也须把仍未结清的两者分别声明。不得因净余额为零省略真实责任。来源须在 cutover 前，类型与方向匹配；每个原始分录只认领一次，剩余金额不得超过原分录金额。金额不守恒、ID／来源重复或引用过期时，错误指向责任文件的具体行。

切换后的还款事件用原 `obligation_id`，报销事件用原 `clearing_id`。缺少期初 ID 时先列待审，再补期初认领。**沿用同一 cutover 查看下个月时，opening 保持原切换日金额**，不手工减去新还款；程序会重放其后的全部已审结算。期初专项卡债仍须按报告日提供覆盖决定；期初外币债务仍须有报告日清偿价值，不能靠结转绕过计价要求。

当前支持有简单同币消费、代垫或已有 Equity 结转来源的期初责任。非消费贷款、复合和跨币来源仍需专门协议，不能补造账务来过关。月报文本／TUI 标出“期初结转”，JSON 的 `actual_spendable.opening_responsibilities` 保留期初金额、来源和审阅位置。

## 单位代垫：钱没报销回来时怎样显示

例如生活费现金 1000 元，替单位付了 500 元，月底只报销 200 元：月报显示可支付现金 **700 元**、待报销代垫 **300 元**。代垫应收不当作可花现金，也不再扣一次本人债务；下月剩余 300 元真实到账后才恢复现金。已审代垫及报销没有个人费用，也不产生新的用途划拨 G。来自专项用途的代垫按该笔资产 `fund` 增减该用途，报销的归属也由真实到账分录确定。

继续使用配置里的 `obligations` 文件：付出两侧来源认领为 `kind: advance_outflow`，报销两侧来源认领为 `kind: advance_reimbursement`，双方使用同一个 `clearing_id` 和审阅理由。还需审定资产分录用途；不能仅凭往来科目余额为正就自动判成单位代垫。当前协议支持一笔同币现金代垫及其多次同币报销；每次报销不得超过该代垫剩余金额。期初已有应收按上一节结转，复合往来仍需后续协议。

月报文本和 TUI 单列待收原币金额、往来账户及原始代垫的文件行号；JSON 在 `report.actual_spendable.clearing_receivables` 保留稳定 ID 和来源。外币应收只列原币，不估算兑换价值；报销后是否可花仍取决于到账账户的支付范围。待报销款不能作为信用卡债务的专用现金覆盖。

同一往来账户同时记录代垫和本人卡债时，程序逐 ID 追踪，核对“账本余额 = 代垫应收 − 本人未偿责任”；即使两者刚好抵消，个人债务仍独立占用实际可花。责任文件里已审的未来报销记录可以保留，历史月报只应用截止日以前的事件；未审的下月报销到下月才列待审。

## 外币未清卡债：账单已经锁定人民币金额

消费的原币和历史费用继续保留。例如消费 100 USD、当时有来源的历史费用 700 CNY，月底银行已锁定清偿 800 CNY：生活费现金 1000 元的实际可花为 **200 元**，历史费用仍为 **700 元**。清偿价只决定债务占用，不代替消费计价，也不提前认作已还款。

在月报配置里加 `debt_settlements: debt-settlements.yaml`。从 `SETTLEMENT_VALUE_MISSING` 待审项复制责任 ID 和完整 `ref`，人工核对银行已锁定的**含费用总额**、有效日期及每份责任的分摊。以下展示文件结构；`purchase_ref: {}` 须替换为完整引用：

```yaml
schema: 6
cutover: '2026-09-01'
as_of: '2026-09-30'
report_currency: CNY
statements:
  - id: card-bill-september
    kind: locked_bill
    locked_on: '2026-09-15'
    valid_until: '2026-10-05'
    report_amount: '800'
    evidence: '银行账单编号或保存位置：已核对含费用的人民币清偿总额'
    reason: '确认本账单覆盖下列责任的全部当前未偿额'
    allocations:
      - obligation_id: card-purchase-1
        purchase_ref: {}
        remaining_native: '100' # 必须等于这笔责任当前全部原币未偿额
        report_amount: '800' # 分摊给这笔责任的人民币清偿额
```

同一账单可分摊给多个责任，合计必须精确等于账单总额；共用的固定手续费只进入总额一次。账单含另行入账的本币费用责任时，也可列入同组，但其分摊额必须等于原本币未偿额。每份责任只能出现一次，同一账单证据不得换个 ID 再计一次。`evidence` 是你的审阅记录，填写可复核的账单编号或存储位置；程序核对声明与账本，不自动向银行核验。

锁定日不能晚于报告日，也不能早于有账本来源的消费日；报告日须在有效期内。部分还款后，旧声明的原币未偿额不再匹配，需要按剩余账单重审；完全还清后删除相应分摊。未来实际换汇／还款的价格不能倒填到尚未锁价的早期报告。明确有来源的零清偿金额可写 `'0'`，缺价不能填零。

尚未锁定金额时，将该组写为 `kind: unlocked`，保留 `id`、`evidence`、`reason`、`allocations`，删除 `locked_on`、`valid_until` 和所有 `report_amount`。程序会明确报告 `SETTLEMENT_PATH_UNSUPPORTED` 实现缺口；当前尚未支持可执行兑换路径、报价和费用的报告日计价。没有任何清偿决定则列数据待审，不能猜测账单已经锁价。

专项资金覆盖仍由 `debt_coverage` 单独决定，此时覆盖金额使用**人民币清偿额**，不能把 100 USD 直接与 100 CNY 比较。预留不改变资产用途余额或净划拨 G。文本和 TUI 同时显示原币未偿及锁定清偿金额；JSON 的 `actual_spendable.settlement_allocations` 保留账单 ID、日期、原币数量、报告货币分摊及审阅行号。任一责任缺价时不提供局部可花数字。

分项入口也支持 `--actual-audit --debt-settlements path/to/debt-settlements.yaml`；来源盘点命令会检查其中的消费引用。已记历史价格的简单两腿外币刷卡现可认证原币责任，两腿原文价格权重仍须精确相等；后续还款仍按已有同币还款及已审购汇协议核对，跨币直接结算和复合责任需要继续实现。

## 专项卡债：明确哪份现金用于偿还

同名的旅游现金和旅游卡债不会自动相抵。有专项未偿卡债时，在月报配置中加 `debt_coverage: debt-coverage.yaml`。覆盖文件需要你确认：所选现金确实可以偿还这笔责任，且未另行预留。支持同一责任使用多份现金，也支持多笔责任分用同一份现金；程序联合校验份额、账户真实余额、用途跨账户净余额和责任未偿额，超额会在覆盖文件的具体行报错，给出实得与容量。

先运行月报的 `--format json`，从 `DEBT_COVERAGE_PENDING` 待审项复制 `obligation_id` 和 `ref`。以下为填写结构；`purchase_ref: {}` 须替换为那份完整的 `ref` 映射，账户与用途 ID 也按自己的已审配置填写：

```yaml
schema: 6
cutover: '2026-09-01'
as_of: '2026-09-30'
report_currency: CNY
decisions:
  - obligation_id: travel-card-1
    purchase_ref: {} # 替换为待审项 ref 的完整映射
    resources:
      - account: Assets:Bank:Travel
        commodity: CNY
        lot: CNY/no-cost
        owner_id: travel
        amount: '100'
    reason: '确认这 100 元可支付并专用于偿还该笔旅游卡债'
```

旅游现金 100、旅游卡债 300、生活费可支付现金 1000 时，明确覆盖 100 后，实际可花为 800，旅游可动用现金为 −200。覆盖 83 元旅游卡债时，旅游可动用现金为 17，生活费实际可花仍为 1000。预留不移动资产，也不产生用途净划拨；实际还款按账本处理。

明确没有专用覆盖时，该责任仍须列一项决定，将 `resources` 写成 `[]`，未偿全额占用实际可花。文件只适用于所写报告日；更新月份、还款或资金位置后重验。责任结清后删除其决定，资金减少后相应释放预留；旧决定不会被自动截减。未结清专项责任缺决定时是数据待审。

分项审计入口支持 `--actual-audit --debt-coverage path/to/debt-coverage.yaml`。月报 JSON 的 `actual_spendable` 中保留 `coverage_allocations`、`obligation_coverage` 与 `purpose_available`；这些金额仅在实际可花认证成功时提供。

报表文字中消费“差额”是目标减实际，负数表示超支；用途“差额”是月划拨目标 Q 减已发生净划拨 G，负数表示超额划拨。外币消费保留原币事实，9 月目标比较可使用经核实的人民币还款成本，不能当作消费日历史汇率。证券池的金额是账面成本用途展示，市值未知。最新 9 月**临时候选**按已确认的钱包期初用途与生活费上限运行：生活费目标 2,000、成本 2,339.58，目标差 −339.58 CNY；用途现金可支付 −21.29 CNY；「最多能花」取较小值 −339.58 CNY。该候选未替换原已审侧文件，不代表历史正式重签。

历史月报只反映报表截止日。截止日之后发生的交易或负债不会倒扣到这份历史报表；若拿它判断今天可花，须另外核对其后的变化。`as_of` 也不能单独证明 importer 已经导入该日的全部流水。

## 新交易导入后先看待审清单

同一份私有配置可生成指定日期区间的来源待审清单：

```bash
PYTHONPATH=src python -m beancount_budget_tool.v6.review_queue \
  --config fixtures/private-ledger/reviews/v6-monthly-report-2026-09.yaml \
  --since 2026-10-01 --through 2026-10-12
```

`--format json` 保留完整 booked 来源引用，方便生成下一份审阅文件。清单按日期列出未认领的费用／收入分类、H 资产用途、负债事件、新账户语义与待定支付范围。经审阅的券商资金池内部买卖不要求逐腿标用途；与池外资金或负债的边界仍列出。清单为空仅表示这些**来源**暂无待办，不证明新月计划、人民币计价、用途库存或首页已经认证。

若所查区间没有已记交易，文字输出另显示最近一笔 booked 交易日期并提醒核对 importer 覆盖范围。交易最晚日期只是观察到的账本事实，不能证明此后真的没有发生交易。

## 续用已确认的私人分类习惯

旧私有 `v6-classification-rules-standing-2026-09.yaml` 记录了当时的分类偏好；它的普通 Income 默认仍是生活费。新需求已把普通 Income 默认改为自由资金，9 月临时候选的 `standing-classification-rules.yaml` 已体现这一点。证券交易费仍归生活费，已明确的证券／余额宝收益和逆回购结息归投资.待投资金，银行结息及已逐笔确认的返现保留原分类。这些规则只在个人侧文件，不写入公共分类器。新返现与尚未明确的金融收入被默认规则排除，留给逐笔审阅；9 月批准的餐饮、交通等账户到子类的映射也只适用于 9 月，没有自动延长。

导入新流水后，可用一条命令续用已审分类、生成**新**侧文件并查看待审清单。原有侧文件不覆盖；新文件会先经分类及待审审计，再写入指定路径：

```bash
PYTHONPATH=src python -m beancount_budget_tool.tools.v6_refresh_review \
  --config path/to/reviewed-month.yaml \
  --rules path/to/matching-approved-rules.yaml \
  --since 2026-10-01 --through 2026-10-12 \
  --output-classifications path/to/classifications-next.yaml
```

规则文件与配置所指的分类文件须使用同一类别名册；新私人规则把普通 Income 默认归自由资金。工具拒绝覆盖输出文件，逐条重验旧认领；新收入若落在返现或未知金融收入账户仍会待审。它不自动认领资产用途、债务、资金池外边界或新月计划。以后要用新分类文件跑完整月报，须在该月报配置里把 `classifications` 指向新文件，并另备该月已审输入。
