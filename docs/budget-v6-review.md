# 预算架构 v6：计划能花，与现在真能花

状态：**v6.0 冻结的实施架构；部分代码已实现，完整端到端验收仍待完成**。当前需求以用户编写的 [REQUIREMENTS](REQUIREMENTS.md) 为准。本文写出输入、计算与拒绝规则；实现进度见[实施状态](v6-implementation-status.md)。只有具体可复现的需求反例、守恒矛盾或重复／漏算才修订计算语义，并同步补验收用例和版本。

## 1. 先说人话：v4 的四个好问题，v6 怎样继续回答

v4 把“生活费、用途目标、实际持有、专题”分开问，这个结构是对的。v6 **保留后三个问题和费用分类**；只把第一问拆开，因为“计划上允许花”与“今天真有钱可以花”不是同一个答案。

| 我想知道什么 | v6 给我的答案 | 这个答案不代表什么 |
|---|---|---|
| **生活费现在实际还能花多少？** | 已认证的日常自由可动用现金，扣除本人全部未获专用覆盖的已发生消费责任及逾期／本月必付责任；首页主数字 | 月计划写了多少，或银行卡余额全都能花 |
| **若生活费计划按时兑现，能花多少？** | 在同一口径下模拟尚未兑现的补给、已批准的流出及其债务／预留影响后，重新计算实际可花；同时列出尚未兑现额 | 钱已经到账，或未来必然到账 |
| **这个月原打算花多少、实际花多少？** | 各消费类别的月目标，对照已分类的净费用；收入补充和退款分别列明 | 某类别没超目标，就证明有现金可支付 |
| **储蓄本月按计划存够了吗？** | 储蓄月划拨目标，对照本月经过认证的**用途净划拨**；首次拨入计一次，同用途搬家计零 | 储蓄账户余额、基金市值或储蓄本金一定还剩这么多 |
| **储蓄现在实际在哪里？** | 可核对的真实资产按账户、商品和成本批次列出属于储蓄的份额；账面累计基金则明确标“真实持有未知” | 这些资产全部可立即变现，或基金账面数就是真实持仓 |
| **这笔钱属于哪个专题？** | `tracking` 可重叠地检索费用、收入等指定度量；合并结果按原事件去重 | 专题是一份新资金，或能把不同度量随意相加 |

这样，v4 的“本月有没有存够”和“储蓄实际在哪里”继续分别回答，不能因为增加首页的实际可花而省掉。消费目标、净费用、收入补充、用途净划拨、真实持有与专题也各自保留，不混成一个万能余额。**实际可花可以为负；证据不足时显示“无法确认”，不能填零。**

例如十月生活费消费目标 2000 元、储蓄划拨目标 900 元，并不是账户里凭空多了 2900 元。月报分别比较生活费目标与净消费、储蓄目标与实际净划拨；储蓄持有另按真实资产查，实际可花另按今天的现金和债务查。

例如已到账 5000 元、明确从日常自由资金划给投资 4000 元、又刷卡消费 300 元：**实际可花 700 元**。另有尚未兑现的生活费补给计划 1000 元时，**计划兑现后可花 1700 元、尚未兑现 1000 元**。首页必须突出“实际 700”；不能把“计划 1700”画成已经拥有的现金。

旧稿的字母只为对照旧代码而保留：`P` 是消费月计划（可联想 *Plan*），`Q` 是用途月划拨目标，`E` 是净费用（可联想 *Expense*），`S` 是收入补充，`G` 是用途净划拨，`H` 是真实持有明细，`K` 是账面累计账户；`R=P+S−E` 是 v4 的**计划口径消费许可**，不是实际可花，也不能直接改名为 v6 的计划兑现后可花。v4 没有解释 `Q/S/G/K` 为什么选这些字母，这里不臆造出处；v6 的正文、报表和界面都使用完整中文名称，不要求读者先背缩写。

## 2. 四条不能跨过的边界

### 2.1 计划不会凭空生钱

计划输入要分成三类，哪怕它们仍放在一个 YAML 文件里：

- **消费类别目标**：本月想把餐饮、交通等支出控制在多少，用于目标对比；它不是资金来源，不自动增加“实际可花”或“计划兑现后可花”。
- **用途划拨目标**：本月想给储蓄、投资、旅行等实际划多少；对比已发生的净划拨。未执行时，不从实际可花扣掉，也不假称资金已进入该用途。
- **生活费补给计划**：将来要有多少原先**尚未计入实际可花**的资金进入日常可花范围。只有这一类的**未兑现部分**可作为“计划兑现后可花”的候选输入；能增加多少还要连同债务、预留和计划流出重算。其来源可以是未来收入、从受保护用途明确释放的资金，或从尚未纳入日常可花范围的真实资金转入；计划必须写明来源类型、生效月、金额及稳定标识，不能从消费类别目标反推。

旧 `budget.yml` 的一条金额究竟是“消费目标”还是“将来要给生活费补钱”，迁移工具只能给提案；无法凭名称、日期或旧 `budget` 标签确定时须人工审阅。**同一个 1000 元不能同时作为两个独立生活费补给计划。**

### 2.2 心里已经决定用途，不等于已经执行划拨

收入到账可先停留在日常自由资金。即使当时已打算用于投资，也不在收入分录里制造一次用途划拨。经使用者确认的**第一次实际资产间专用转移**，才把资金从自由状态转入投资等受保护用途；同用途在银行卡、余额宝、券商或基金之间继续搬家，只改变位置，不再次划拨。若第一次资产转账只是自由资金从数字钱包搬到银行卡，仍不是投资划拨。不可用“最近三天同金额”自动认领首次转移。

“资金属于谁”与“在哪个账户”是两回事：一张银行卡可以同时有自由现金、旅行余款和储蓄。不能因为账户名叫“日常”就把所有分录都当自由现金；也不能因为基金名叫“投资”就把里面的储蓄改成投资。个人账户语义及例外写在私有、可审阅的声明中，不写死到通用算法。

### 2.3 记了消费，与付了现金，是不同时间的事

现金付款：费用发生，现金减少。信用卡／白条购买：费用和待偿债务发生，现金尚未减少，但**实际可花必须立即为这笔未清偿开支减少**。以后还款：现金减少、债务减少，实际可花不因此再少一次，也不产生第二笔消费。退款则按原负费用和实际退款到账分别处理；尚未到账的退款不能先当现金。

长期贷款不能将全部未还本金一次减作“本月实际可花”。逾期／本月必付的贷款切片、信用卡全部已发生未偿消费、已经专门预留的还款现金要按同一责任 ID 配对，做到**一笔义务恰好占用一次**；即使费用归旅行等受保护用途，专用现金不足时的缺口也不能从首页消失。贷款发放的现金不得只因落入银行卡就自动视为日常自由资金：其受限用途和还款责任须先确认。没有期限、来源或预留依据时不签发精确“实际可花”。

### 2.4 基金账面累计不是能花的现金

只有申购、赎回金额、没有可信份额／净值的基金账户称为**账面累计账户**（旧稿记作 `K`）。其正、零、负余额都不能证明基金市值、剩余本金、是否清仓、可赎回金额或收益。因此它不能直接进入实际可花，也不能按账户余额给几个用途分库存。真实到账的赎回现金，经过用途确认后，才进入相应用途的真实现金；若仍受保护，也不自动成为日常可花。

## 3. 三本分开的账，以及唯一的连接

### 3.1 财务事实账：现实发生了什么

Beancount 官方 loader／booking 后的交易、分录、金额、商品、成本批次、资产和负债余额是财务事实。预算工具不改这些事实，不补造基金收益，不靠预算标签纠正仍配平的金额错误。完整账本及来源 ID、日期、交易顺序是审核基础；整笔漏导入和金额录错由 importer／人工对账负责。

资产按**完整账户、商品、成本批次、时间点**核对。可验证数量的现金、证券等叫“真实持有”；基金账面累计单列，不与真实持有相加。真实现金再按受保护用途或自由状态分切片，每一分必须有唯一归属。外币、证券当前是否可兑换／出售，与历史消费、用途划拨的计价是两种证据；缺任一必要报价时，相关报告保持不可用，不用今日汇率冒充历史成交，也不用历史成本冒充今天可花金额。

### 3.2 预算计划账：原本想怎样安排

计划文件只记录明确的消费目标、用途划拨目标、生活费补给计划及其生效期间，不读取普通交易来倒推“本月原计划”。金额必须是明确的十进制数，月键、币种、覆盖及覆写规则唯一；缺计划不是零计划。可另存账本内专门的计划记录，但不能复用普通收入或资产转账上的旧 `budget` 标签。

对每一期生活费补给计划，记录**稳定计划 ID、计划金额、生效与到期时间、来源身份和类别、来源可供金额、其在报告时点是否已计入实际可花及判断依据、已兑现／已取消／未兑现切片**。来源可以是未来收入的有身份预期，也可以是当前不在自由现金里的真实资产切片；“未来可能有工资”可以是条件假设，不能同时让两份计划无约束地占用同一个预期来源。来源与计划之间按金额切片建立容量关系：一笔工资到账 2000 可以用不重叠的 800、1200 分别兑现两份计划，但同一元不能兑现两次。两份尚未兑现的计划竞争一笔已知资产时，**计划时就联合校验容量**，不能等到账后才发现超分配。

兑现只是一条把计划切片与真实财务事件／经批准的资金状态变化相连的关系，不生成 Beancount Income，也不直接给实际可花“加一笔钱”。实际可花始终由资产、责任和覆盖状态重算。部分兑现允许；有效兑现总额加取消额不得超过该计划，超出部分应另行记录为无计划的实际增量或明确修订计划。取消余下 600 不抹掉此前已兑现 400；延期保留同一计划身份，新月份的独立补给另建期次；到账被追回时现金按真实事实减少，是否恢复原计划须有明确修订，不自动再承诺一笔未来收入。每次兑现／撤销都记来源切片、计划切片、生效时点与逆向引用，旧报表可回放。

同一来源**金额切片**不能兑现两份计划；同一收入若已经使可动用现金增加，兑现登记只减少“尚未兑现”，**不得再次增加实际现金**。若计划对应的资金在报告时点已计入实际可花，必须把相应计划切片认作已兑现或纠正来源；没有来源身份、计入状态和依据时，不给完整计划兑现后数字。钱曾经自由、后来确实转入受保护用途，未来再明确释放时可以形成新的净可花增量；这里禁止的是**同一时点重复计入**，不是要求这笔钱历史上从未自由过。

### 3.3 预算事实账：哪些钱可动用、欠了多少、归谁

首页承诺的范围固定为**本人、明确配置的单一报告货币、已结算且可直接用于日常支付的真实现金**，并覆盖本人全部已发生消费责任以及逾期和本月必须偿付的非消费责任。当前账本可选择 CNY；换成其它报告货币时，同一套规则按所选货币运行。每个曾直接记账的真实资产账户须有人审阅其支付能力与商品；余额宝等可核对余额的真实资产是否属于首页支付范围，是**第二个决定**，不能把“不纳入首页”误说成“它不是基金申赎的真实现金对手”。受保护用途份额、账面累计基金、证券、未结算卖出款、应收款、不可提现信用余额和受限借款资金均不成为日常自由现金；已结算银行／钱包资产也还须按每份归属及限制审阅。未标注资产腿**默认待审，不默认自由**；`fund:"-"` 只表示用途未指定，不证明现金已结算或可支付。

所谓**已发生消费责任**，是本人在刷卡、白条、分期或其它形成应付款的购买中已经承担、尚未结清的全部金额；账单日、分期、最低还款和逾期只改变它的状态或到期切片，不能复制出第二份责任，也不能因分期只保留本月应还部分而释放剩余消费债务。**非消费责任**首版只纳入有合同／账单证据的贷款本月应还本金、本月应付的已确定利息与手续费，以及全部逾期额；不把未来全部房贷本金一次扣光。本月账单已经确定、但 Beancount 尚未计提的应付利息，也凭账单建立一次有来源的付款责任；后来实际计提时关联**同一责任 ID**，绝不再增一份。合同／账单仍无法确定本月应付金额时待审，不能按零处理或猜预计利息。已形成的罚息须作为有来源的新责任。押金与他人欠我的钱是应收而不是现金；预付、钱包充值和代付须先按真实资产、负债、归属及是否可支付分类，不能靠叙述自动创造现金或债务。名单之外的责任类型或不明确的本人承担份额待审，不能静默不扣。

每份责任都有稳定 ID、原生币种、已发生金额、未偿余额、本人承担份额、用途、来源 posting／协议、到期与逾期状态。混合用途卡债需逐份分割；清偿 100 元时必须指定消耗哪一份，或使用事先批准、对此账户有效且确定的清偿规则，不按任意 FIFO／账户名猜。所有责任逐账户及原生币种核对：`期末未偿 = 期初未偿 + 新增 − 已清偿 − 有证据的退款／减免 ± 有证据的责任转移`。已 booked 的负债须与对应 Beancount 账户核对；仅账单已确定、尚未 booked 的应付利息先在**独立责任记录**中与账单核对，不伪造 Beancount posting，也不拿它填 booked 负债余额。待真实计提入账时，将 posting 绑定原责任 ID 并由“账单证据”转为“已 booked 证据”，总未偿责任不得跳增。账单中的“本期到期 300”只是原责任的引用切片，不能与其“已发生 300”再相加；原始责任和到期切片若重叠认领即拒绝。cutover 期初未偿、逾期和分期关系须一并审阅，不因过了月初消失。

**专用预留／覆盖**是当前确实存在、可用于清偿某责任的支付资源切片与该责任切片之间的独占关系；只写“我以前存过 300”不算覆盖。每个时点检查资源仍存在且可支付、同一资源总覆盖不超其当前数量、同一责任总覆盖不超未偿数。已覆盖资源从其原属的自由或命名用途可动用现金中移除，相应责任只扣未覆盖部分；释放预留时资源与未覆盖责任同步恢复，不能生钱。同属“旅行”的现金与卡债**不因名称相同自动形成覆盖**；须有明确的责任—资源分配，或经批准、可逐笔展开且容量通过的私人规则。银行已扣但发卡方尚未销账的还款，只有在有真实、独占且仍有效的在途结算证据时，才作为该责任的覆盖；否则暂停签发受影响的实际可花，不声称“还款不双扣”已成立。结算、退款、减免、在途完成与预留释放必须原子更新。结清后的卡内正余额不是负债，若不可提现便不是自由现金；实际提回银行后才按到账处理。

**用途可动用现金**单列为“该用途已认证、当前可支付的真实现金 − 该用途已独占预留给债务的现金 − 该用途已发生责任中尚无专用覆盖的金额”，可以为负；它不等于基金持有。同一义务的覆盖额已从可动用现金扣掉，不能再从未覆盖责任扣第二次。用途刷卡购买时增加债务占用，但真实现金持有和用途净划拨均暂不改变；实际清偿或真实资金离开该用途边界时才按财务事实改变用途净划拨。其他用途的专用现金若不足以覆盖其债务，剩余缺口也进入首页的**全局未覆盖责任**：旅行现金 100 经批准全额覆盖旅行欠款 300 中的 100、日常自由现金 1000，则旅行可动用现金 **−200**，首页实际可花 **800**，不是 1000。这只是披露本人须偿付的压力，不擅自把 200 划给旅行，也不生成用途净划拨。若尚未决定这 100 元是否真能用于偿债，不能直接套用 800，受影响的首页数字待审。

在给定**报告时点**及本月义务期限后，先按责任 ID 去重、完成独占覆盖，再算首页。设“自由现金”是已认证且未保护／未预留的可支付真实现金；“未覆盖责任”是本人承诺范围内全部已发生消费责任，加逾期与本月到期的非消费责任的**并集**，每份只取未被有效专用资源覆盖的部分：

```text
实际可花 = 自由现金 − Σ逐份、去重后的未覆盖责任之当前清偿价值

尚未兑现的生活费补给
  = 已批准的有效补给金额 − 已兑现切片 − 已取消切片

计划兑现后可花
  = 在同一时点口径和计划期限内，联合执行已批准且相互兼容的
    补给与计划流出、同步更新现金／责任／预留之后，重新计算的实际可花
```

最后一式是**条件情景**，不是保证将来到账；只有每项计划已证明是独立的净可花增量、彼此来源容量不冲突、无责任／预留副作用时，才可简写为“当前实际可花＋未兑现净补给−未执行净流出”。未来工资可作为有唯一身份、金额和归属的预期来源进入情景，仍标“未兑现”，不假称已有现金。解除 1000 元还款预留同时使 1000 元债务重新未覆盖，净增量是 **0**；两份计划各要从同一笔仅有 1000 元的受保护现金释放 800，联合情景须拒绝，不可报 1600 或静默截成 1000。仅有储蓄月目标而未执行，不自动生成计划流出；真正已批准的未来划出计划须进入情景，不能只写散文。缺期初现金、资金归属、负债、当前清偿价、有效覆盖，或计划来源是否已计入实际无法判断时，相应完整数字显示“无法确认”，不填零或旧缓存。

## 4. 把例子从头走一遍

下表假定期初日常可动用现金和相关债务都是 0，币种均为 CNY；同时存在“尚未兑现的生活费补给计划 1000”，其**来源身份已声明为与到账 5000 不同、尚未进入自由现金的独立净补给**，并且没有其它未来计划流出。缺少这项来源声明时，不能照抄表中计划数字。

| 已发生事件 | 自由可动用现金 | 尚未清偿／预留覆盖之外的日常债务 | 实际可花 | 未兑现计划 | 计划兑现后可花 |
|---|---:|---:|---:|---:|---:|
| 先写下生活费补给计划 1000，钱还没到 | 0 | 0 | **0** | 1000 | **1000** |
| 收入实际到账 5000，先归自由现金 | 5000 | 0 | **5000** | 1000 | **6000** |
| 第一次明确划给投资 4000 | 1000 | 0 | **1000** | 1000 | **2000** |
| 信用卡购买日常用品 300，未还款 | 1000 | 300 | **700** | 1000 | **1700** |
| 从自由现金还这 300，债务也结清 | 700 | 0 | **700** | 1000 | **1700** |
| 另有真实来源兑现计划中的 400，且原先不在实际可花内 | 1100 | 0 | **1100** | 600 | **1700** |
| 再兑现余下 600 | 1700 | 0 | **1700** | 0 | **1700** |

若只是在两张**已经都计入自由可动用现金**的银行卡之间搬 400 元，第四行的实际仍为 700；这不能算一次新的兑现。收入到账时“我知道 4000 将来用于投资”也不提前改变第二行；确认转账时才改变第三行。若计划的 1000 原本就是第二行已计入的 5000 的一部分，第二行就必须把该计划认作已兑现，不能继续显示“计划 6000”。**同一场景不能同时采用互相矛盾的计划来源解释。**

在“实际 700、独立净补给未兑现 1000”的同一时点，若还有一笔**已批准但尚未发生、不同源**的生活费流出计划 500，情景重算的“计划兑现后可花”应为 **1200**。如果所谓 1000 补给只是解除既有 1000 元还债预留，解除同时恢复同额未覆盖债务，计划净贡献是 0，不能继续报 1700。

实际可花与类别目标可以不同。例如消费目标只剩 100，但实际自由现金还有 700，应并列显示“目标剩 100、实际可花 700”，不以 `min` 偷换任一数字；这不是鼓励超目标消费，而是让使用者同时看见目标与现实。

## 5. 费用、划拨和专题各怎么算

费用归类记录回答“买了什么”。一条费用可拆餐饮 80／交通 120，拆分的原币金额精确加回原 posting；退款写负费用，冲减原类别的净消费，不伪装为新收入。价保、返现、报销若源账本来就是 Income，则作为收入事实分类一次；正 Income 冲回原补充，不用名字猜。本人批准“日常 Income 默认补生活费”的私人规则，可按有效期展开成**逐 posting 可见、可覆盖、可追溯**的分类；本金归还若账上是应收结算，不因银行卡到账就被创造为 Income。

**同一份经济利益不能同时作为退款冲减净费用，又作为价保／返现收入增加补充。** 每笔负费用或补充收入保留其真实到账／债务减免的原始证据引用；若两种分类试图认领**同一来源金额切片**，拒绝并请人选择真实记账方式。若是两笔分别到账、各有独立来源的 20 元，则确实是两笔事实，各自照计；不能仅凭日期或金额相同跨交易自动去重。若 importer 把同一笔银行流水重复记成两笔会计交易，这是源账错误，仍由 importer／人工对账处理；可靠外部流水 ID 冲突可作为诊断证据，但预算器不假装能找出所有漏导入或重复导入。

资金用途记录回答“这份钱要留给谁”。真实资产切片逐笔守恒；从自由资金到储蓄、投资等用途，记一次用途净划拨；同用途搬家为零；明确解除用途时反向记。用途月目标只与这个已认证的净划拨比较，不被称为“期末本金”。从受保护用途付实际消费会减少该用途的真实现金与用途净划拨，但不会自动把钱退回日常自由资金；不能用所有用途净划拨简单修补实际可花。

消费分类、资金用途、实际可花中的债务占用可以同在一笔购买里，各自只记**自己的投影**。例如旅行现金 100 元，买旅行用品 83 元：旅行净费用 +83，旅行现金剩 17，日常实际可花不受影响；若刷卡买 83 元，旅行现金暂时仍 100，**另经批准将其中 83 元独占预留给这笔卡债**，则旅行可动用现金为 17，日常实际可花也不受影响，**用途净划拨要到真实还款边界才减少**。清偿时现金和责任一起减少，可动用金额不再扣第二次。若只知道“旅行现金 100、旅行卡债 83”，却未证明现金能支付该卡债及其覆盖关系，不得因用途名相同就宣称首页不受影响。若旅行欠 300 而旅行现金只有 100，余下 200 仍压低全局首页数字，不能藏在旅行的负数里。费用确实由投资账户支付但用户规定“证券交易摩擦费归生活费”时，费用类别与付款资金 owner 可不同；这不授权凭类别自动重写资金归属，须明确债务／资金承担关系。

`tracking` 只是一个可重叠的专题索引，不创造计划、用途或收入。完全预算外的费用仍能进入专题实花；预算内和预算外分列，专题合计按同一费用切片的唯一 ID 去重。某专题跨月时逐事件归发生月，不把月末持有量相加。

## 6. 混合用途账面累计基金：只认证事件，不编造库存

账面累计账户可以同时承载旅行、保险、电子产品等用途，不能再假设整账户只有一个 owner。用户逐笔审阅申购／赎回用途切片；每条切片明确引用实际基金 posting、真实现金 posting、商品、同一币种的精确金额和来源。两边切片各自精确加回原 posting，并明确哪份现金对应哪份用途；不能按 FIFO、比例或金额相近自动猜。账户账面数仍逐 posting 精确核对，但**用途切片不是基金内部的真实持仓余额**。

账户声明仍由人按**完整账户名**审核：币种、固定无成本 lot、cutover 前 booked 累计与人工确认的期初、有效期、账户记法（例如申购减赎回式）和是否批准简单现金申赎模板。零余额账户、有直接 posting 的父账户以及正余额基金一样要审；账户外形、名称和余额符号都不能代替语义判断。一个有效期间的账户类型唯一；以后任何一腿出现成本 lot、价格、其它币种或非零非现金调整，须重新审阅并按首版拒绝，不可只挑合规腿继续算。**与单用途 schema 5 不同，v6 的账户声明不绑定全户唯一 owner**：单用途简写也须展开为逐事件用途，混合账户才不会被假装拆成多个真实基金库存。账面累计变为零不证明清仓；不同账户的账面数既不与真实持有相加，也不跨账户合并成基金总额。

首个可签发模板只收同一原始交易的一条账面累计账户腿与一条真实现金腿、同报告货币、等额反向、无费用／Income／其它资产腿，并经用户确认该账户此类交易是申购／赎回。现金腿确定真实现金增减及实际可花是否变化；基金腿的用途只说明当次意图。同用途从基金赎到现金再回投，不是第二次用途划拨。申购 500 可确认旅行 200／保险 300；赎回 100 可确认全来自旅行，随后花 83、保留 17：基金内部旅行现值仍**未知**，真实旅行现金 17 则可认证。未知历史用途不必否定用户对**当次**赎回的明确决定，但不得借此签发完整基金持有；当次用途也不明确则该事件的受影响预算数字待审。

## 7. 正式签发的证据与拒绝规则

- 所有输入都带版本、稳定 ID、完整源引用和相关依赖指纹。账本只改变无关交易，不强迫所有旧决定重审；影响某决定的 posting、金额、顺序、配置或证明变了，该决定失效。禁止相同 posting／切片被两份冲突的声明重复认领。
- 原始 Beancount 必须由官方 loader 验证；同日 booking 顺序是财务事实。同一交易的分录可拆切片，但所有切片按原商品、符号和金额守恒。费用、收入、现金、用途、债务、计划兑现各有独立投影；一笔事实可支撑多个不同问题，不能在同一问题里算两次。
- 费用与收入的历史报告价值取可追溯的原始交易总价或执行价及对应证据；拆成多切片时按原数量比例精确分配，所有切片（含预算外）价值相加必须等于原值，计算中不先舍入。成本仅用于财务 booking／lot，不自动等于当时实付价或用途边界价。非现金用途边界需事件专属价值证据。外币、证券的“今天可花”又需要**时点可兑现价值**，不能复用旧成交价。缺证据报缺项，不能猜或仅改类别标签补价。
- “实际可花”只对配置中完整覆盖的真实可动用资产、自由切片、相关负债和债务预留签发；基金账面累计和未结算证券不填入现金。已知部分可列明细，不能用它冒充完整总额。缺账户、负债或来源分类时应标“无法确认”，而不是过度乐观的余额。预算超支或实际缺口本身是可报告结果，不是为了看起来正常而改账。
- 对每个计划兑现，检查有效兑现额与取消额之和不大于计划额、对应净增量未在该时点实际可花中重复计入、同一**来源金额切片**只兑现一次、部分兑现之和守恒；一笔收入事件可拆成互不重叠的切片兑现多份计划。转账跨越“可花范围”边界时一出一入精确对应。自由现金透支、用途归属透支、债务预留重复占用、不同用途错误合并均给出可定位错误。对真实现金的边界签发与账面累计基金的真实市值未知要分别标能力状态。

报告提供“正式可签发／待审预览”两种明显不同的状态。正式结果按**度量、用途、期间、报告时点、首页支付范围**附来源和可用性；若某事件缺少归属，受其影响的实际可花／计划可花不能给完整数字。只有基金持仓未知而所有现金、计划和事件边界均已认证时，可签发现金预算，同时明确标记基金完整持有未知。**实际可花与计划兑现后可花分别签发**：计划来源缺失只阻断计划数，不得抹掉已核实的实际数；实际数依赖的现金或责任缺失则不能签发实际数。完整 v6 首页须通过两数各自所需的现金、责任、覆盖、计价、计划及源账依赖；阶段性仅完成费用分类时，可单独发布名为“已认证净费用”的有限报告合同，不能把它包装为完整首页。“已知部分现金明细”也另名、列全未知候选与排除理由，不显示成完整“实际可花”。**实际可花为负是可签发的准确结果**，与范围不完整、待审或计算错误是不同状态；旧缓存、空值和 0 均不得伪装为已认证结果。

诊断至少区分：重复／遗漏责任认领、覆盖资源失效或超额、在途证据不足、清偿分配不明、用途偿付缺口、来源容量竞争、计划来源已计入实际但未兑现、计划流出漏入情景、当前清偿价缺失或过期、报告时点不一致、支付范围未审、非法交易级标签与非法 `fund` 语法。实现须给稳定错误码，例如 `DUPLICATE_OBLIGATION_CLAIM`、`OBLIGATION_UNCLAIMED`、`COVERAGE_RESOURCE_INVALID`、`PLAN_SOURCE_OVERALLOCATED`、`CROSS_PROJECTION_DOUBLE_COUNT` 和 `SETTLEMENT_VALUE_MISSING`；错误信息同时给源引用、受影响金额和人工修法，不能把不同错误统统叫“预算不支持”。

机器可读的**能力记录**最少含 `metric`（如 `actual_spendable`、`planned_spendable`、`net_expense`、`known_cash_detail`）、`scope`、`as_of`、`status`、`reason_codes` 与来源引用。`status` 封闭为 `CERTIFIED`（该度量与范围有唯一数值，**允许负数**）、`UNKNOWN`（真实值在源数据中不可得，例如账面累计基金市值）、`NEEDS_REVIEW`（证据可补但尚未批准）、`UNSUPPORTED`（首版协议明确不支持）和 `INVALID`（源事实或守恒冲突）。除 `CERTIFIED` 外不得在该度量的正式位置显示数值；“已知部分现金明细”是**另一个 `metric` 和显式较窄的 `scope`**，不是完整实际可花的降级状态。发布合同的机器类型封闭为 `COMPLETE_HOME`、`CERTIFIED_EXPENSE`、`KNOWN_CASH_DETAIL`：前者须分别检查两项首页度量，后两者不得借用前者的名称或样式。未来增加度量／合同须升输出 schema，不能复用旧枚举的隐藏含义。

阻断签发的顶层 `reason_code` 家族封闭为 `SOURCE_INVALID`（loader／原文／booked 映射不可信）、`CLAIM_INVALID`（分类／归属／跨投影认领冲突）、`VALUATION_MISSING`（必要历史或当前价值缺失／过期）、`SCOPE_PENDING`（支付范围或期初未审）、`OBLIGATION_INVALID`（责任缺失、重复或清偿不明）、`COVERAGE_INVALID`（预留／在途资源不守恒）、`PLAN_INVALID`（来源、容量、兑现或情景冲突）、`TIME_INVALID`（时点、到期、顺序或版本不一致）、`UNSUPPORTED_EVENT`（范围内事件无首版协议）。稳定的细项错误码可随实现增加，但必须映射到上述唯一家族和受影响的能力记录；例如多计划**未实现**报 `UNSUPPORTED_EVENT`，只有实证超额才报 `PLAN_SOURCE_OVERALLOCATED`。拒绝整个源快照的 `INVALID` 与某项度量的 `NEEDS_REVIEW`／`UNSUPPORTED` 不得混用。

## 8. 从 v4 继承的输入合同：每笔事写在哪一层

本节把 v4 中仍合理的**正式输入规则**直接写入 v6。账本是财务事实，posting metadata 是最简单的预算输入；复杂拆分与证明放在工具生成、供人审阅的侧文件。下面的示例各自独立，相关账户应先在 Beancount 中 `open`，也不意味着现有程序已经会读取 v6 侧文件。

### 8.1 分录上三个键；计划不借用它们

| 键 | 只可写在哪里 | 回答什么；不回答什么 |
|---|---|---|
| `budget` | `Expenses`／`Income` 的**具体 posting** | 一个已注册消费类别，或 `"-"` 明确预算外；费用/收入的分类，不是资产 owner、生活费补给计划或到账现金证明 |
| `fund` | 真实库存 `Assets` 的**具体 posting** | `"-"` 是已确认的未指定用途；裸用途名是该用途持有变化；`用途\|划拨` 是主动跨用途边界；`用途\|损益` 是有证据的非划拨变化。它不声明账户是否可立即支付 |
| `tracking` | 交易或 posting | 半角逗号分隔的专题名；只筛选结果，不创造消费、现金、用途或计划 |

首个 posting 前的 metadata 属于交易，posting 下方缩进的 metadata 才属于该 posting。交易级 `budget`／`fund`、空值、重复 metadata 键、未知用途、未知后缀、多于一个 `|`、保留键注入都拒绝。`fund:"用途|期初"` 非法，期初另有快照。**这些是 v6 工具自己的原文层校验责任**：不能以“Beancount loader 没报错”为通过，loader 会接受其中一些预算层非法写法。工具还要拒绝未覆盖的资产腿／费用腿；未标注是待审，不是 `fund:"-"`、`budget:"-"` 或自由可花。`|损益` 必须有利息等真实外部原因；不能把普通购物贴成“损益”来躲避用途净划拨。标签是人的意图声明，组证据只能证伪，不能静默把 `|划拨` 换成另一种原因。

```beancount
2026-10-03 * "买菜"
  Expenses:Food 300 CNY
    budget: "生活费.餐饮"
  Assets:Daily -300 CNY
    fund: "-"

2026-10-05 * "第一次留给储蓄"
  Assets:Daily -1000 CNY
    fund: "-"
  Assets:SaveA 1000 CNY
    fund: "储蓄|划拨"

2026-10-06 * "储蓄只换了银行"
  Assets:SaveA -1000 CNY
    fund: "储蓄"
  Assets:SaveB 1000 CNY
    fund: "储蓄"
```

第一笔只记餐饮净费用并减少真实现金；第二笔储蓄净划拨增加 1000，日常实际可花减少 1000；第三笔储蓄净划拨是 0，持有位置从 A 变 B。若餐饮消费改刷信用卡，仍在购买日记净费用和债务占用，还款日不再记费用。

同一显示名可以在消费类别、用途、专题三份名册中分别使用；实际存储用稳定 ID。输入名先 NFC 规范化、去首尾空白，`.` 只作消费类别／用途的层级分隔，段内不能含 `.`、`|`、半角或全角逗号及控制字符。`tracking` 只按半角逗号分词、去重；全角逗号在正式运行时拒绝，迁移工具可提出修正。改名保留历史别名与原 ID，不靠近似名称重认。

v4 的省事办法也保留，但只能用于**经人确认、在完整有效月份内从来不承载命名用途份额**的账户／商品：显式“全为未指定用途”策略为每条资产腿生成可见的 `fund:"-"` 等价审计记录；同义的行内 `fund:"-"` 可共存，命名用途的行内或侧文件归属一旦出现，整段策略失效并要求逐腿处理。它绝不能按账户名称默认储蓄／投资；普通银行卡若暂存赎回后仍属于旅行的 17 元，也不得继续使用该策略。策略只管**用途归属**，不会替 v6 决定这个账户的现金是否已结算、可支付或已被债务预留。
策略生效区间和账户／商品进入依赖指纹；每次运行重放该区间全部 booked posting 与期初归属，区间中途出现可见命名用途份额时**整段失效**、生成逐腿待审提案，不能只从发现那天起改默认。程序不能检测账本和审阅输入都没有记录的“心里想法”，这仍是人的标注责任；不靠把策略改成自动猜测来掩饰。

### 8.2 侧文件各有职责，不能一个字段包办全部

迁移和审阅界面可以生成以下**逻辑记录类型**；具体 YAML/JSON 编码由实现版本固定，但每类的权威职责不能互换：

| 记录 | 只能决定或证明什么 |
|---|---|
| 消费分类切片 | 一条已 booked 的 `Expenses`／`Income` posting 怎样拆到多个类别及明确预算外部分 |
| 真实资产归属切片 | 一条已 booked 的真实 `Assets` posting 中，原生单位各属于哪个用途或未指定用途 |
| 经济组及证据分摊 | 已有资产切片、费用、收入、负债或权益证据怎样组成**同一交易内**的事件；只引用，不重写分类或 owner |
| 计价绑定 | 某费用切片、原文总价分配或用途边界采用哪份有来源的历史价值 |
| 独立真实资产归属转移 | 同账户／商品／完整 lot 的份额在两用途之间转移；不生成第二份财务资产 |
| 账户语义声明 | 每个曾直接记账的资产账户属于真实库存还是账面累计；账面累计账户没有全户唯一用途 owner |
| 账面累计申赎用途切片 | 某一次申购／赎回每份现金属于哪个用途，以及与真实现金腿的对应关系；不声称基金内部有等额真实库存 |
| 支付范围声明 | 完整账户／商品、有效期、是否能直接支付、限制与来源；不改变真实库存类型或资产用途 |
| 责任记录 | 稳定责任 ID、账本／合同来源、原生币种、本人份额、用途、未偿数量、消费／非消费类型、到期与逾期；账单只引用原责任切片 |
| 独占覆盖与清偿分配 | 当前真实支付资源／在途结算怎样独占覆盖责任切片，真实还款、退款、减免、转移又消耗哪份责任；不能产生第二份资产或责任 |
| 当前清偿计价 | 已锁定账单金额或有效的时点清偿路径、汇率、费用和来源；不与历史消费价混用 |
| 经济利益来源切片 | 退款、价保或其它补充各认领哪份真实到账／债务减免证据；同一金额切片不能跨净费用和收入补充重复受益，同额独立来源允许并存 |
| 生活费补给计划与兑现 | 期次、来源身份与容量、是否已计入实际及依据、计划流出、真实事件与计划间不重叠的兑现切片、取消／延期／撤销；不创造 Beancount 交易 |

每条 `Expenses`／`Income` booked 子腿由行内 `budget` **或**一份外部分类切片完整认领，每条真实 `Assets` 子腿由行内 `fund` **或**一份外部归属切片完整认领；二者不能同时决定同一域，即使写相同结果也拒绝。组记录可以引用已归属／已分类切片，不算再次认领。账面累计账户 posting 由账户语义和**事件用途切片**处理，与普通 inline `fund`、真实持有归属、未指定用途自动策略互斥。每份切片与原 posting 同币种同符号、原生数量精确加回，不能一条 200 元分录给两个类别各 200。

外部声明须引用**来源内容**，不能只用日期金额或行号：原文引用包括相对根账本路径、原始交易文本 SHA-256、同文件相同文本的出现序号和原文 posting 序号；booked 引用再加 booking 子序号、完整 lot 键与事实哈希。上述序号从 1 起，按冻结原文及官方 loader 顺序编号。插件或 `pad` 生成的 posting 用生成它的指令引用、生成类型／序号和 loader 版本，不信任合成 posting 的文件行号。切片引用附在 booked 或生成引用上。相同内容的两笔真实交易照计两次；`^link` 可供导航，不是去重 ID。追加无关交易须重算报告，但相关原文、lot 历史、名册和计价语义没变时不要求人重新审同一决定；真正依赖变化才使审批失效。

## 9. 从 v4 继承的计算合同：组、价格、时间与守恒

### 9.1 自动组有限，复杂事必须有证据

分类、归属、经济组、计价是四个域，按此顺序输入与核验，不能从会计配平直接推用途。自动组只在**同一原始财务交易**中、对已经切好的 posting 做以下有限判断，不跨交易找相近金额：

1. 没有命名用途资产：普通消费／收入／借款本金等交易，仍完整分类费用收入；无资产腿的刷卡消费合法。
2. 单一用途、商品和完整 lot，所有裸用途资产腿的原生数量和为零，且无未解释对手：组成一个规范的多对多**同用途搬移**，不虚构哪笔转出对应哪笔转入。
3. 恰好一条 `用途|划拨` 资产腿，和恰好一条等额反向报告币种未指定用途资产腿或真实费用／收入／负债对手：组成简单用途边界事件。
4. 恰好一条 `用途|损益` 报告币种现金腿，和一条等额反向真实 Income：组成简单非划拨收益事件；普通 Expenses 不能借此模板放行。
5. 同一用途恰好两条裸资产腿，现金／外币与证券／另一币种相配，无费用、收入、负债、权益，成本权重按币种精确抵消且 lot 唯一：组成简单买卖或换汇，净划拨为零。
6. `exact_costed_sale_group_v1` 来源协议：任意多个负数证券成本批次、一条正数报告货币现金、一条报告货币 Income，以及零条或多条非负报告货币费用，全部属于同一原始交易；证券成本须完整、正数且使用报告货币，现金／Income／费用不带价格或成本，证券报价若有也须是报告货币。逐批核对并保存完整 booked 引用、数量及成本，精确满足「实收＝Σ 成本本金＋损益－Σ 费用」；Income 为正是亏损，为零可为持平，空白 Income 由固定版本 loader 补齐后按其 booked 数值核对。符合该模板时由程序构造完整显式来源组，不要求人再次批准数学等式；旧的人工来源组记录仍须验证且不得重复计入。此自动化只证明来源和原币等式，不能选择 budget、推断 fund、认领本金用途、制造 G 或签发可支付能力。额外对手、混合币种、缺成本或有残差时不得只挑部分腿放行。

条件重叠报歧义；模板之外必须有明确组类型、全部成员、真实财务对手、证据分摊、计价角色与各类型守恒证明。每份资产切片恰好属于一个最终经济事件，费用／收入证据在**用途归因域**最多分配一次；同一费用既用于“净费用统计”又作为该组的真实原因，是不同投影，不叫双计。借款本金的资产／负债组不凭空造 Income，权益／`pad` 也不凭空造第二份资产。跨月转账需真实 Transit 科目在各月闭合，不能跨交易搜索一对金额抵消。

证券卖出同时有收益、手续费时，先把所得现金认作原投资用途，在显式经济组中解释证券、现金、手续费和收益；再用锚定于这笔已 booked 交易之后的独立归属转移，决定是否把其中多少现金退出投资。**不能**让卖出现金直接贴未指定用途，再让预算器猜出一段虚拟投资现金并重复计算。带成本资产即使是买入且没写 `@`，只要有费用／收入对手，也需要显式组。用途转移须核对转出份额足额、转出转入同原生数量且共享同一历史边界价值。

组守恒按类型，而不是只看整笔金额为零：同用途搬移按同商品、同 lot 原生数量和为零；投资买卖按每个商品的会计成本权重加真实财务对手精确配平；主动划拨须有真实资产或费用／收入／负债／权益对手解释来源去向；独立归属转移不改变 booked 财务资产总量。一个组不得拿另一笔交易的 Income 或费用填自己的缺口。多种合法解释若会改变原因、金额或来源，仍要人选择，不能因为最后净额碰巧相同就自动放行。账面累计账户只使用 §6 的独立申赎模板，不偷偷落入上述真实库存模板。

2026-10-26 增补 `native_income_payable_v1`：一笔原始交易含唯一正数 H 资产收款、唯一负数 Liabilities 应付款，以及一条或多条同向 Income；全部同币种、无成本／价格，须逐原币精确满足「到账＝Income 净收入＋新增应付款」。应付款不充作收入，整笔不产生 G。收款资产明确归唯一已登记 fund 用途时，新增责任沿该用途登记，并绑定所有 booked 来源；这是已记等式与显式用途的推导，不是代替使用者批准不确定用途。尚未转交的金额压低实际可花；部分与跨月转交只减少已发生的对应责任，不重复记费用、收入或 G。仅当同账户／同币种有唯一未结的此类应付款、无未审期初及代垫混淆，且实际资产付款不超过剩余责任时，可自动关联；多份未结、超额或来源不足仍待审，不按人名、摘要或相同金额猜配，也不拿未来付款冲销过去责任。转交资产未写 fund 时按默认支出用途，债务关联仍独立核对。fund 仍只能写 Assets；多用途责任未决定、跨币、价格／成本或额外不支持的对手不套用此协议。

### 9.2 四种价格各管一件事

配置必须选**一个**报告货币，且它是根账本有效 `operating_currency` 中的一个；若有 CNY、USD、HKD、JPY，不能默选第一个。消费目标、划拨目标、净费用、收入补充、用途净划拨和生活费补给计划都以报告货币呈现；真实持有保留原商品和完整 lot，账面累计只在各账户自己的原生单位内核对。原生数量、Beancount 成本权重、交易时历史价值、报告时点可兑换／可支付价值是**四种不同的数**。

一条需计入预算或专题的 `Expenses`／`Income` posting，其历史价值依次取：①原文在该腿写明、与报告货币一致的 `@@` **总价**或 `@` 单价；②若原生单位就是报告货币，取原生数量；③否则取唯一、有事件来源的实际支付分摊；④再否则取唯一、有时点和来源的事件报价。③和④同时存在而未声明只作交叉核对时，报来源冲突；缺价时报缺项。明确 `@ 0` 不是缺价。完全预算外且没有专题金额需求的腿可不做历史计价；一旦专题要显示它的花费，仍须计价。支付现金 700 与费用原文 `@@710` 可能由 10 元折扣 Income 平衡，不能擅自把费用改成 700；想冲减净费用须在真实账务中写负费用。

同一 posting 拆分类时，**先**定该腿唯一有符号历史总价，再按原生数量比例精确分给各切片，预算外切片也分到自己的部分，所有切片价值之和等于原总价。例如 `100 USD @@ 700 CNY` 分餐饮 60 USD、旅游 40 USD，分别是 420／280 CNY；旅游若预算外，餐饮预算仍只取 420，专题可按来源范围显示 420＋280。若支付凭证表明切片实际单价各不相同，必须逐切片提供唯一支付分摊，而非再按比例猜。数量为零不能用比例除法，只有原值与每个切片值都证明为零才放行。精确十进制／有理数计算到输出，展示时才舍入。

用途划拨的历史价值只取**边界事件时点**：报告币种现金用原生金额；外币现金、证券和其他非现金资产要事件专属边界价。成本权重和现价都不是兜底；同一用途转出／转入共用一个价值证明。零执行价允许有证据的零价值处置，不等于缺失；零价值的非现金用途划拨须有人确认原因。原文证据层在 parser 丢失之前保留 `@`、`@@`、`{}`、`{{}}` 的形式与精度；`@@` 被 booking 拆 lot 时要精确分摊原文总额。需精确认定 `{{总成本}}` 的命名用途组首版拒绝，不能反乘近似单价。官方 loader 有 error 或仍存在真实非零会计残差时，不为预算签发；仅原文总价可证明的规范化表示差可被解释，不能用它掩盖真实残差。

“今天实际可花”的外币若被用户纳入范围，另需**报告时点可支付或可兑换的价值**及费用／限制证据；不能拿上一次购物的历史价或证券成本顶替。外币**责任**另有清偿价值：若账单已锁定报告货币实付总额，以该总额为权威；否则须有报告时点可执行的清偿路径、汇率、固定及比例费用、有效期和来源。历史购物 `100 USD` 当时记净费用 700 CNY，而现在清偿要 800 CNY 时，费用仍是 700，实际可花须扣 800。多笔责任共用固定换汇费时只分配一次；有同币种可专用现金时按实际清偿路径核对，不强迫虚构两次兑换。首版允许仅正式签发**报告货币现金及已锁定报告货币清偿额**的完整首页；存在未锁定外币责任而缺当前清偿证据时，首页待审，即使用户把外币**资产**排除在支付范围外也不能忽略那笔债务。

首页承诺的是**明确配置的直接支付范围**，不是整份净资产：基金账面累计、证券、应收等经审定不可直接支付的资产合法地不进入首页，不叫“漏算”；范围及排除理由须同屏可见。尚未审定、却可能属于该范围的真实货币账户，或用户声称可支付却缺时点报价的外币资产，不能用“排除”绕过完整性校验；只能显示**另名的已知部分明细**并同时列出未知账户，不能冒称完整“实际可花”。合成外汇平衡腿、旧成本和文字备注不是可执行报价；只能采纳有时点、交易路径与来源的独立价格证据。

### 9.3 月首起点、事件顺序与两类存量

最早可签发的预算 `cutover` 必须是自然月第一天、当天交易前。此前历史只用于核对真实库存／账面累计期初，以及期初仍未清偿责任、在途付款和已预留资源；不重新签发旧月份的费用和划拨。**已完成自然月的月报**取该月最后一日日末状态；**本月实时页**取查询指定日期的日末（未指定时为配置时区的本地今天日末），必须显示该 `as_of`，不冒充完整月报。`obligation_horizon` 是 `as_of` 所在自然月最后一日日末（含当日），此前全部未清逾期另行持续纳入；已发生消费责任的全部未偿额不受期限过滤。所有并列的实际、计划、债务、现金和用途数字用同一 `as_of`；完整自然月才可对比消费目标和用途目标，任意日区间仍可看已发生流量与时点存量。包含 cutover 前日期的“v6 正式报告”拒绝。

计算输入固定为 `(as_of, obligation_horizon, scenario_horizon, report_timezone, policy_version)`：财务状态只应用生效日期不晚于 `as_of` 的已 booked 事实，不把未来日期分录提前到账。首版非消费贷款的义务期限取 `as_of` 所在自然月最后一日日末，加上此前全部未清逾期；已发生消费责任的全部未偿金额不受账单日或期限过滤。本月实时页的计划情景期限默认同月末；已完成月份的“计划兑现后”是**当月已批准计划若按期兑现的反事实对照**，即使实际没兑现也保留未兑现差额，不追认真实收入。计划情景按各计划声明的生效时点、真实 booked 事件的既定顺序逐事件重放；同一时点不能确定先后而结果可能不同时待审，不允许从月末余额倒推一个方便的执行顺序。逾期未兑现计划若要继续进入未来月份的预测，须明确继续有效、延期或取消，不能自动变成到账或在下月再复制一份。`report_timezone` 为用户配置的 IANA 时区，用它判断月末与到期日；当前用户可配置 `Asia/Shanghai`，通用内核不写死。日历推进、到期变化、报价过期、冻结解除或计划到期，即使账本字节没变，也须生成新时点快照和缓存键；历史报表连同当时的政策版本可精确回放。

官方 loader／booking 顺序先确定 FIFO lot；预算层不得靠重排同日交易改变财务事实。若原始文件同日排列与独立的逐笔余额记录冲突，只能在留存证据的迁移副本中修正源文件顺序、产生新快照并重新校验所有来源声明，不能在预算计算时暗中排序。独立归属转移锚定某笔已 booked 交易**之后**或 cutover；同日先后会影响库存合法性而无足够证据时拒绝。同一原子交易整体应用后检查，不在两条 posting 之间造半笔透支。

**2026-10-25 显式现金顺序输入补充（budget-order v1）**：已确认实际先后、但不同 include 文件行号使现金充值晚于付款时，允许在源交易级写整数 `budget-order`，作为同一日期无成本普通交易的重放顺序；未填为 0，值小先行，同值保留官方顺序。仅调整预算重放中的先后，不改官方已 booked 的任何金额、账户、价格、成本、源行或引用规则；不得标记成本交易或自动 pad，也不得跨越这些事件，不重做 FIFO／booking。缺少声明时保持原顺序，禁止从负数或日末余额自动推断充值在先。跨日及真实库存不足继续拒绝。该字段须显式写在源交易中，禁止 pushmeta 注入，来源内容改变后的原认领仍须重新校验。其他 Beancount 客户端不因此改变显示顺序。此补充解决已知顺序的输入表达，不新增日内透支宽免。

真实库存期初由 booked 财务数量逐账户、商品、完整 lot 核对，只在这些已有数量上分未指定用途与各受保护用途；期初归属**不新造资产、不追认历史净划拨**。通常每个原子事件结束时，同一真实坐标满足：`已 booked 资产数量 = 未指定用途份额 + 各命名用途份额之和`，各真实份额非负；真实负库存／卖空首版拒绝。负债保留在 Beancount 的 Liabilities，不塞进真实持有。账面累计坐标单独满足：`账面期末 = 经核对期初 + 本期逐 posting 有符号变动`，允许负数，但不做真实持有分解。账户正、零、负都须经人工确认语义，带直接 posting 的父账户也单独审阅，不能只列负数账户或按名字猜类型。账面累计各账户不能跨户求和；同一用途若关联它，完整真实持有、基金市值、收益与净资产为未知，真实现金／证券已知明细仍可单列，不能称为完整总额。

**滚动证券资金池的账户用途展示例外**：经用户批准的、全部排除直接支付的 H 账户可组成一个资金池，声明固定受保护本金、保护用途、剩余用途和账户展示顺序。程序仍按完整 lot 核真实持有，但用途展示可按整个池的 booked 报告币种成本权重自动分配，不要求给 importer 的每笔逆回购或卖出 lot 手工贴用途。cutover 及之后每笔 booked 交易完成时，池总成本必须足额覆盖保护本金；否则阻断。日末先按声明顺序从各账户成本额容纳本金，余下归剩余用途：若券商现金账户有 X 元且 X≥3000 元，可显示“额外储蓄 3000 元、待投资金 X−3000 元”；现金不足 3000 元时，其余保护额显示在同池证券账户的账面成本中。自动重排只是账户分布约定，不产生月度净划拨 G，也不代表某个具体证券 lot 属于储蓄。投资收益的预算分类仍独立判断。证券现值、可变现额和具体储蓄份额缺时点证据时保持未知，不能把成本展示拿来计算实际可花。私人规则只需在池账户、保护额或顺序改变时重新审阅；正常 importer 增加交易应自动审计，不要求用户逐笔维护用途。

**2026-10-11 用户批准的严格同日还卡结算例外**：若某已审真实银行资产的外币坐标原为零，booked 顺序先发生信用卡还款、后发生同日购汇，允许在两笔之间短时出现与还款等额的负数，但它是未完成结算敞口，不是可花 H。必须逐事件声明白名单信用卡完整负债账户，并分别绑定还款时资产扣款、同笔负债减少及之后购汇入账的完整 booked 来源；同商品金额精确相等，购汇有明确 `@@` 报告货币总价和同笔等额报告货币借记腿，之前信用卡已有足额负债，同坐标中途无其它交易，当日日末精确回零。缺证据、跨日、金额不等、来源复用或额外透支仍拒绝。白名单只允许这些逐笔通过的结算桥，不宽免信用卡所有交易或普通资产负库存。信用卡负债本身照常可为负；例外针对还款后的银行外币资产。账户审计仅验证该桥的 booked 形状和库存恢复，后续责任清偿分配、用途及完整首页仍需单独认证；本版报表只取日末，不签发桥接中途的可花数。

计划输入继续用版本化、严格的 YAML 或等价专门记录：月键必须是**带引号的 `YYYY-MM`**、金额为精确十进制字符串、币种匹配报告货币；拒绝 YAML 日期类型、重复键、`null`、未知字段及文字中偷藏月份。默认模板、从指定月份生效的模板、指定月份覆写三层按字段覆盖；没有交易的月份仍展开计划。**活跃**消费类别／用途定义为：该月有计划声明，或该月有对应分类／用途投影行。活跃消费类别须有明确数字目标（允许 0），或被明确的祖先**子树总目标**覆盖；受覆盖子类别可只显示支出明细，不伪造独立目标。未获任何目标覆盖仍是待审，不能把缺失当作 0。用途月目标是明确数字或显式“不考核目标”，缺失不是 0。v6 新增的生活费补给计划另列，不能拿旧消费目标自动生成。每个月先独立计算，再汇成连续月份；已发生费用／净划拨可按期间相加，真实持有和实际可花都是**时点数**，不能把各月末余额相加；计划兑现记录绑定自己的发生时点，跨月未兑现份额按版本化计划继续或取消。

消费类别和用途分别用稳定 ID 建树；`expense_targets` 是节点**直接**目标，未另设子树总目标时，汇总节点把本节点直接目标与各子节点目标各计一次。`expense_subtree_targets` 是明确约束本节点**及全部后代**净费用的独立上限；有它时以该上限比较整棵子树，不再把后代目标加到这项上限。子节点若另有目标，可独立比较，但同一金额不得在父节点上限里再加一次。首版不改已有 ID 的父节点；改名保留原 ID 与历史别名。若将来要按今天的树重述旧月，必须另选报告基准与版本，不能悄悄改历史。

## 10. 从零实现与迁移：依赖顺序比一次性重写更重要

**首次发薪前的目标适用范围**：首个已配置发薪日定义该消费目标政策的生效起点，之前可只签出已有范围的账务、用途及资金审计，周期状态须标明尚未生效，不输出周期剩额或最多能花，也不编造周期起点或零额度。配置表完全为空仍是缺少生效范围，须待审。该规则不推断更早是否存在工资或改变工资财务归属；工资对应上月劳动报酬时，周期依然依据实际到账日。账务证据不足、真实负库存及责任未审等阻断照常生效。

**2026-10-25 已确认的消费目标周期补充**：账务按自然月审核不强制消费上限也按自然月。使用者可显式选择发薪周期作为消费目标口径，保存真实发薪日及各周期目标；含本次发薪日、不含下一发薪日，末周期不猜下一次日期。月末快照的最多能花取已审可支付资金与月末所在发薪周期截至该月末的目标差之较小值；跨月不重置目标，不使用月末之后的真实交易。自然月目标可不考核，若保留则独立显示，不折算、不替换周期目标。多月报告保留每个月末的周期状态，不相加重复覆盖的周期目标或余额。该选择不改变资产用途、责任、划拨 G、cutover 或月末资料完整性的确认；周期先于已审范围、缺额度或缺消费证据仍须待审，不把缺失消费当零。周期独立查询只签发消费与目标差，实际可支付能力仍由对应时点的资金审计签发。

下面是**实施顺序**，不是声称现有代码已经做到。每一步以自动探针和真实账本副本回测验收，再开放下一个正式度量；旧 Rust TUI 不能在其中任何一步把旧算法改名叫 v6。

| 阶段 | 先完成的产物 | 为下一阶段提供什么 |
|---|---|---|
| 1. 冻结源事实 | 根账本 include 闭包、原文价格／成本证据、固定官方 loader 版本、原文与 booked 的稳定映射 | 后续分类不靠行号、相似金额或不稳定的合成 posting metadata |
| 2. 明确账户和期初 | 报告货币、cutover、全部直接记账资产账户的真实库存／账面累计语义、逐 lot 真实期初、逐账户账面累计期初、负债及可动用范围 | 持有、现金与债务计算有完整边界，负基金账面数不冒充持仓 |
| 3. 编译旧预算核心 | 费用／收入分类、真实资产归属、有限经济组、历史计价、月消费目标／用途目标、专题；先签净费用、收入补充、用途净划拨、真实已知持有 | v4 合理的四问有可验证答案，不把本阶段的目标余额叫“实际可花” |
| 4. 扩展账面累计 | 多用途逐事件申赎切片、真实现金对应、未知能力传播；仅已证明的简单现金事件自动处理 | 混合基金能认证现金用途，而不产生虚构基金库存 |
| 5. 增加首页新口径 | 可支付自由现金、逐用途债务占用与预留、计划补给及兑现、实际／计划双数字 | 5000／4000／300／1000 链可算 700／1700，并防还款与兑现双计 |
| 6. 接日常界面 | 审阅建议、批量确认、局部失效重验、同一已验证快照驱动 TUI／CLI／JSON／CSV | 不让用户手写数百份侧文件，正式数字与诊断同源 |

每阶段都从旧账本**副本**生成带源哈希的待审提案：旧交易级 `budget` 分成类别、用途、专题或计划的候选，多桶金额精确分切片，旧计划日期／文字月份人工解释，历史基金标签可辅助认领**意图**但不证明现值。个人规则如“日常 Income 默认补生活费”“储蓄本金受保护、利息归投资”属于经批准、有生效期的私有规则，展开后每条源 posting 的决定可见；不能写死在通用内核。所有更改保留原账户、金额、成本、日期、link、备注和 `comment` metadata；不自动修正真实账务。旧新报告不用数值相等，但每项差异要能回链事实、计划或人工决定。

本版正式快照包含账户／商品／lot 的原生数量、逐事件精确历史价值、分类、归属、账面累计、债务占用、计划兑现、能力状态和来源依赖；TUI、CLI、JSON、CSV 只读同一快照。loader、归属、组、计价、真实库存、账面累计、债务或计划兑现必需校验失败时，正式签发阻断；可显示标有**未签发**的调试预览。基金完整持有未知是一种有范围的支持状态，不豁免其他错误。每条错误至少给稳定错误码、原文／booked 源位置、期望与实得、受影响度量／期间及人工修法；输出缓存按源快照失效，异步 TUI 用代际 ID 防旧结果覆盖新结果。

## 11. 使用：普通人不需要手写一堆协议

日常界面用普通问题提问：“这笔是消费还是退款？”“从哪份钱付？”“这次是第一次留给某用途，还是原用途搬家？”“这个计划的 1000 元是哪笔真实资金兑现的？”“刷卡债务由哪份钱承担？”对简单场景只需确认建议；复杂证券、混合基金、外币才展开切片与证据。预览即时展示实际可花、计划兑现后可花、未兑现、类别支出、用途变化及不能签发的原因。

通用内核不内置私人的“日常 Income 默认生活费”“储蓄收益归投资”“券商储蓄本金不计息”等规则；它们作为用户批准、有有效期、可覆盖、可追溯的私人输入。旧交易级 `budget` 拆成费用类别、资金用途、计划或专题的候选，旧标签本身不能直接当 v6 证明。真实账本先在副本上迁移、回测、对账；不改原交易金额、账户、日期、备注或个人 `comment` metadata。现在的 Python 简单交易预览、混合基金只读审阅、Rust TUI 均**不是** v6 生产实现。

## 12. 用来打破本架构的验收清单

1. 上文 5000／4000／300／1000 全链：实际 700、计划 1700、未兑现 1000；还卡不再扣；兑现 400 后实际 1100、计划 1700、未兑现 600；同一现金内部转账不得冒充兑现。
2. 消费目标 1000 而没有生活费补给计划时，不能凭目标让实际或预测多 1000；已经计入实际的收入也不能在补给计划里保持“未兑现”。
3. 收入到账时仅有用途意图，不划拨；第一次明确专用资产转移才划拨一次；同用途再搬三次仍只算一次。储蓄本金的私人保护规则不被投资账户名覆盖。
4. 现金购买与刷卡购买对实际可花都立即起作用；还卡不双扣；退款未到账不提前增加现金；当期房贷预留与现有预留不能双扣，全部房贷本金不一次扣光。
5. 应收本金回款虽非 Income，也能因真实、未保护现金到账增加实际可花；Income 即使被分类为生活费，若钱尚未成为可动用现金，不能凭分类增加实际。
6. 旅行现金 100→花 83→余 17，及旅行刷卡 83→还款；日常自由资金不错误增加或减少。混合基金申购 500 分 200／300、赎回 100、花 83、回投 17，不发明基金市值或多算划拨。
7. 负费用退款、Income 价保、正 Income 冲回、证券手续费、完全预算外专题、外币缺历史价格、部分未知基金历史与当次用途未知，分别给出正确数字或明确待审。
8. 计划跨月、部分兑现、延期、取消、来源复用、转账范围误判、负债漏载、报价变化、旧审阅依赖过期、真实现金或用途透支均有稳定诊断；范围不完整时不能签发“实际可花”。
9. 自由现金 1000、刷卡 300 且同笔本月到期，首页 **700** 而不是 400；改为分期后全部已发生未偿消费仍占用；罚息 58.20 需有新责任。账单确定本月须付利息 50、尚未 booked 时先占用 50，后来计提并绑定同一责任后仍只占用 50。现金 1000／债 300 的 300 元预留、释放与还款在途均不得凭状态变化使实际可花离开 700；失去在途证据则待审。
10. 旅行现金 100 经确认专用覆盖旅行欠 300 中的 100、自由现金 1000：首页 **800**、旅行用途可动用现金 **−200**，但不生成一笔 200 的用途划拨。旅行刷卡 83 并用可支付的旅行现金独占覆盖时，旅行可动用现金为 17、日常首页不变；用途净划拨暂不减少，真正用旅行钱还卡时才减少。未证明覆盖时不可按同名用途自动假定它存在。
11. 实际 700、独立净补给计划 1000、另有已批准计划流出 500：计划情景 **1200**；释放专门还债的 1000 预留，债务重新未覆盖，净补给 **0**；两计划各占同一真实 1000 的 800 要拒绝。工资到账 2000 可用不重叠 800／1200 兑现两计划，取消余下部分不抹掉历史兑现。
12. 十月月报无论何日运行均取十月末日末；实时页带明确时点。十月贷款应还 3000、已还 1000，十一月又应还 3000 时，十一月初保留 2000 逾期，绝不只扣新到期 3000。时点、到期和报价有效期变化即使源账不变也重算缓存。
13. 外币刷卡历史净费用 700 CNY、当前清偿需 800 CNY，费用仍 700、实际占用 800；缺当前清偿证据则完整首页待审。已确认不可即时支付的证券与账面累计基金不进首页，但全部纳入／排除账户与理由可见；尚未审定的货币账户不能静默排除。
14. 同一来源金额切片不能既冲减原费用又作为另一笔收入补生活费；两笔确实独立到账的同额 20 元照计两笔，不按相似金额去重。无 `fund` 的资产腿待审，`fund:"-"` 不自动证明可支付；整月未指定用途策略中途出现命名用途即全段失效。

**架构判断**：在已声明来源、账户支付范围、责任及计划事件的前提下，上述验收链条有唯一处理路径，且没有要求编造 Beancount 财务事实或基金持仓。缺声明应给明确待审，不能选一个方便的数字。它们仍是待实现、待 v6 内核测试与真实账本副本端到端验证的设计承诺，不是通过现有旧测试就已兑现的功能。

## 13. 两份复审的裁决，以及仍须由人提供的事实

**已确认的产品选择（2026-10-10）**：用户要求首页表示“不超支仍安全可花”，因此其他用途的已发生债务若缺专用还款资源，缺口也压低首页主数字。旅行专款 100、旅行卡债 300、日常自由现金 1000，且这 100 元确实可用于该卡债并已独占覆盖时，首页为 **800**、旅行用途可动用现金为 **−200**；不是 1000。这是偿付压力，不暗中执行一笔用途划拨。

- **采纳共同的硬缺口**：债务按身份取并集、覆盖资源逐时点守恒、跨用途缺口进入安全可花、计划按净变化联合模拟、报告时点及逾期进入输入、外币责任用当前清偿价。两份审阅分别以不同反例击中了这些问题，不能退让为“先给近似首页”。
- **额度池不单独新增**：此前“1000 计划＋2000 到账−1500 划拨＝1500”的说法，若 1000 是用户后来明确的**未兑现生活费补给**，则 v6 并列报“实际 500、计划兑现后 1500”；若它只是消费类别目标，计划兑现后仍为 500，目标另列。原例没有说清计划类型及收入／划拨发生状态，不能用它强迫增加第三套“额度池”，也不能把 1500 冒充眼下实际可花。本人已明确实际为主、计划兑现后并列；如将来另要求独立额度池，须另升版本并给出不同于这两数的验收需求。
- **不按金额自动去重经济事实**：同一个来源切片不得同时制造负费用与收入补充；不同来源的真实两笔照计。整笔漏导入、重复导入或金额虽错仍配平，仍属 importer／人工输入边界。无需发明“同日同额即同一事件”的规则。
- **真实库存和首页支付范围分轴**：余额宝若经人确认有可核对真实余额，可作为账面累计基金申赎的真实现金对手；它是否可在报告时点直接支付，另外审阅。基金模板“外形匹配”不等于事件用途、期初、来源和价值都已获批准，更不等于可正式签发；首页范围排除也不自动把它变成账面累计账户。
- **范围与未知分开**：经明确声明不可即时支付的证券、基金账面累计、应收等是完整首页承诺范围之外，不是缺失输入；可能可支付却未审的货币账户才导致完整首页不可用。另名的“已知部分”可供迁移审阅，并须同屏列出未知与已排除清单，不冒充完整安全可花。

仍需用户／账本迁移逐项给出的，是**事实输入**而非要求临时决定算法：每个直接记账账户的真实库存或账面累计语义、真实现金账户的支付范围（尤其余额宝）、cutover 期初及尚未清偿责任、生活费补给计划逐期的真实含义和来源身份、旧多用途标签对应的用途、各笔复杂交易／外币清偿的证据。原始计划文件里一项“生活费 1000”究竟是消费目标还是未来补给，不能从名称推断；无法确认就保持待审，不在文档里替用户选择。**这些未完成前，v6 可以作正式架构草案，却不能签发那份真实账本的完整首页。**
