# v6 源码导读（人话版）

> 这份文档不解释"应该怎么用"（那看 README 和 CONFIGURATION.md），只回答一个问题：
> **这堆代码到底在干嘛，我该从哪儿看起。**
> 所有行号/模块名都对应仓库当前版本（`src/beancount_budget_tool/`）。

## 0. 先看两组数字，你就不会慌了

| | 数量 |
|---|---|
| Python 文件 | **86 个**（v6/ 59 + tools/ 17 + 顶层 10） |
| 代码行数 | **约 1.59 万行** |

| 你日常要敲的命令 | **1 条** |

所以"看不懂"不是你的问题：**复杂度全在"证据引擎"里，而那部分你不需要读**。

## 一句话架构

```
你的两个文件（config.yml + budgets.yml）+ 你的账本
        │
        │  ① 简化层：自动填表 / 编译（simple_config.py）
        ▼
14 个证据文件（.budget-state / 临时目录，不用你碰）
        │
        │  ② 证据引擎：8 个独立审计各自核对、各自认证
        ▼
月报（全部认证） 或 待审清单（带文件:行号，逐条说缺什么）
        │
        │  ③ 你的决定
        └──→ 存回 .budget-state/reviews.json.gz → 下次重算复用
```

**引擎没变过，是前面加了一层"自动填表器"**。这就是为什么代码看起来有两套东西。

## 1. 先认清三条车道

代码里同时存在三套入口，这是"多"的第一来源：

| 车道 | 命令 | 你要给什么 | 什么时候用 | 代码入口 |
|---|---|---|---|---|
| **日常（推荐）** | `python -m beancount_budget_tool --config config.yml --month YYYY-MM` | `config.yml` + `budgets.yml` + 账本 | 每天看数、每月记账 | `launcher.py` → `simple_config.py` |
| **高级（完整）** | `beancount-budget-tool --config month.yaml` | `month.yaml` + 13 个侧文件 | 需要逐指标控制、旧配置 | `v6/monthly_report.py: main` |
| **迁移（一次性）** | `... init` / `next-month` / `review-month` | `setup.yaml` / `next-month.yaml` | 清理历史账本时 | `tools/v6_*.py` |

- 车道一和车道二**共用同一个证据引擎**；车道二的配置可以被车道一"接管"（`configure --from-config`）。
- 车道三的 17 个工具都只做"生成表格/检查改动"，**不签发数字**。

> 结论：想读代码，只读"车道一 → 引擎 → 输出"这条线，其余都是历史兼容和迁移辅助。

## 3. 一条命令的完整旅程（跟代码走一遍）

以 `python -m beancount_budget_tool --config config.yml --month 2026-09` 为例：

| 步 | 发生了什么 | 代码位置 |
|---|---|---|
| 1 | 解析子命令（默认 `monthly`） | `launcher.py: main` + `COMMANDS` 字典 |
| 2 | 发现配置是 schema 1（两文件）→ 走简化层 | `simple_config.is_simple` |
| 3 | 读 `config.yml` + `budgets.yml` + `.budget-state` 里已审记录 | `simple_config._documents` / `_baseline` |
| 4 | **在临时目录里自动生成首月填写表**（复用迁移工具 `v6_init.create_setup`），并替你填好：默认用途、账户语义/支付范围、期初、目标、两个确认开关 | `simple_config.build_runtime` |
| 5 | 把填写表编译成 **14 个证据文件**（accounts/opening/ownership/classifications/obligations/...） | `v6_init.compile_setup` |
| 6 | 合并 `.budget-state` 里你的历史决定 → 得到"本月最新已审配置" | `simple_config` + `state_store` |
| 7 | 进入统一入口 `audit_month_workflow`（它会判断走两文件还是旧配置） | `monthly_report.py:229` |
| 8 | **第一道待审**：`audit_review_queue`——账本标签/来源级问题（交易级标签、语法、未知字段）。有就直接只输出待审清单 | `review_queue.py` |
| 9 | **第二道：月报审计** `audit_reviewed_month`，校验配置字段/版本/日期/文件存在性 | `monthly_report.py:111` |
| 10 | 对所有输入文件算 **sha256**（运行期间防篡改） | `monthly_report.py:160` 附近 |
| 11 | 冻结账本解析和事实索引 | `financial.frozen_financial` / `facts.frozen_fact_indices` |
| 12 | **跑 8 个独立审计**（见下） | `monthly_report.py:169-190` |
| 13 | 汇总三个 headline：账户用途、用途余额、最多能花 | `summarize_account_purposes` / `summarize_purpose_balances` / `summarize_max_spendable` |
| 14 | 检查 8 个审计的 `ledger_snapshot` 是否同一账本（否则 `MONTH_REPORT_MISMATCH`）；再算一次输入哈希（变了 `INPUT_CHANGED`） | 同上 |
| 15 | **第二道待审**：有指标未认证 → 把指标级阻塞翻译成具体待审项 | `metric_review.enrich_metric_reviews` |
| 16 | 输出：全认证 → `render_text` 月报；否则 → `render_workflow_text` 待审清单 | `monthly_report.py:387/322` |

> **两段式待审**是理解输出行为的关键：
> - 第一段（`review_queue`）挡"账本本身写错/没写清楚"——例如交易级 `budget`、标签写错位置；
> - 第二段（`metric_review`）挡"指标缺证据"——例如某笔资产用途没定、某类别没目标。
> 两段的输出格式一样（带 `文件:行号`），但修复方式不同：前者改账本，后者填表/做决定。

这 8 个审计是：

```
audit_actual_snapshot       → 可花（现金 − 债务 − 覆盖 + 完整性声明）
audit_monthly_expense_targets → 消费目标 vs 实际（targets.py）
audit_monthly_purpose_progress → 划拨目标 Q vs 实际 G（purpose_progress.py）
audit_purpose_pools         → 资金池保护（purpose_pools.py）
audit_k_book_purposes       → K 账户账面用途（k_book_purposes.py）
audit_h_holdings            → 每账户用途切片（holdings.py）
audit_monthly_tracking      → 专题（tracking.py）
audit_default_outflows      → 默认支出用途收付（default_outflows.py）
（可选）audit_plan           → 工资周期口径（salary_plan.py）
```

**每个审计都是"只读 + 自证"**：自己加载账本、自己算、自己返回 `ledger_snapshot` 和认证状态。
`monthly_report` 只负责"拼起来 + 检查它们来自同一份账本"。

## 4. 六个核心机制（代码多的真正原因）

### 4.1 身份是哈希，不是行号

`refs.py` 里一个"事实引用"长这样：

```python
BookedRef(path, transaction_sha256, occurrence,
          posting_ordinal, booked_ordinal, lot, fact_sha256)
```

- `transaction_sha256`：这笔交易**原文内容**的哈希
- `occurrence`：完全相同的交易里第几次出现（防止复制粘贴歧义）
- `posting_ordinal` / `booked_ordinal`：原文第几条分录 / booked 后第几条
- `lot` / `fact_sha256`：成本批次 + booked 事实指纹

行号只是给人看的诊断信息（源码注释原话：*Line numbers are diagnostics only*）。

**为什么这么做**：你的审阅决定（claim）绑定的是"这条交易的这个分录"。
账本一改，哈希变，旧决定自动失效（`SOURCE_REF_STALE`）——避免"改了金额但审阅记录还生效"的事故。

`facts.py` 负责把账本里每个 booked 事实映射到引用。特殊情况：Beancount 的 `pad` 会生成没有原文分录的 booked 交易，
它用 `GeneratedTransactionRef` 锚定到 pad 指令 + **loader 版本**（这就是为什么到处有 `loader_version`）。

### 4.2 三个快照，保证"证据属于同一份账本"

| 快照 | 怎么算 | 防什么 |
|---|---|---|
| `ledger_snapshot` | include 闭包里每个文件 sha256 + loader 版本 → 再 sha256（`financial._digest`） | 8 个审计必须同一版本账本 |
| 输入文件哈希 | 运行前后各对 config + 13 个侧文件算 sha256 | 运行期间改配置（`INPUT_CHANGED`） |
| `review_sha256` | 已审决定集合的哈希 | 决定和证据对不上 |

### 4.3 纯计算和举证分离（最值得学的一点）

`core.py: calculate_actual` 是**纯函数**：不看账本、不读文件，输入 `ActualInput`（资源/义务/覆盖/范围/证据），
输出 `ActualReport`。它只负责算法和校验：

- 资源按用途并集、义务按 ID、覆盖不能超配（`COVERAGE_RESOURCE_OVERALLOCATED`）
- 未知范围、缺清偿价、缺证据 → 返回 `NEEDS_REVIEW`，**不填 0**
- 负值也是合法签发结果（表示超支）

而"从账本和侧文件编译出 `ActualInput`"是 `actual_snapshot.py` 的事，它在编译层做举证：
现金审计、债务审计、外币折算、预留覆盖、完整性声明各自完成，凑不齐就不给数字。

> 源码原话：*此函数不从财务账推断账户是否完整，那是编译层的举证责任。*

### 4.4 每个指标独立认证，不完整就不出数

每个 `audit_*` 返回同一个形状：`{status, ledger_snapshot, review_items, reason_codes, ...}`。

- `status = CERTIFIED` → 才有数字
- `status = NEEDS_REVIEW` → 数字字段是 `None`，同时给出**具体待审位置**

`metric_review.enrich_metric_reviews` 再把"指标级阻塞"翻译成"文件级待审项"：
每条带 `reason_code + source + ref + 相关字段`，这就是你看到的待审清单。
所以待审清单不是"报错日志"，而是**一张带来源引用的填表任务**。

### 4.5 原文边界：引擎跑之前先挡一道

`source.py` 在账本层面做最后一道过滤：

| 检查 | 结果 |
|---|---|
| 交易级 `budget` / `fund`（v6 不允许） | `TAG_LEVEL_FORBIDDEN` |
| `budget` 写在资产腿 / `fund` 写在费用腿 | `TAG_LEVEL_FORBIDDEN` |
| 行内金额语法（多用途拆分）不合法 | `FUND_GRAMMAR` |
| `tracking` 写金额 | `TRACKING_INVALID` |

**为什么值得单独一层**：这些是"账本本身写错了"，和"预算算不出来"是两类问题；
先挡掉，后面引擎就不必到处防御。

### 4.6 一个业务概念 = 一个模块

59 个模块不是乱拆的，是**每个业务概念一个只读审计**：
归属（ownership）、持有（holdings）、转账协议（h_transfers）、外币（h_fx）、
基金申赎（k_events）、预算目标（targets）、划拨 G（purpose_flows）、计划兑现（purpose_progress）……

想加一种新业务？照着任意一个 `audit_*` 写新模块，在 `monthly_report` 里挂一行，在 `metric_review.SOURCES` 加映射即可。

## 8. 一个诚实的评价：哪些复杂度是必要的

**必要的**（去掉就会错）：

- 引用/快照机制（否则审阅决定会和改过的账本错配）
- 纯计算与举证分离（否则算法里会混进 IO 和猜测）
- 指标独立认证（否则会拿部分结果冒充全量）
- 原文边界校验（否则错误在深层才暴露）

**历史包袱**（可以减，但作者为了兼容没减）：

- **三套入口并存**：`configure` 简化层、`month.yaml` 完整层、`init/next-month` 迁移层
- **59 个模块**里约 10 个是"同一概念的变体"（`tui_*` 5 个、`project` 与 `project_actions` 职责重叠）
- **17 个迁移工具**，一半是一次性脚本
- 每个模块的 docstring 都是英文契约说明，**没有中文注释和中层文档**——这大概就是你觉得"看不懂"的直接原因

如果目标是"读得懂"，我的建议是：**给 `monthly_report.audit_reviewed_month`、`core.calculate_actual`、`facts.py` 三个地方补中文注释**（约 30 处），比给 59 个模块都加注释有用得多。

## 附：术语对照（文档/代码里那些怪词）

| 词 | 人话 |
|---|---|
| 证据（evidence）/ 快照（snapshot） | 每个数字背后的来源引用 + 账本版本哈希 |
| 认证（certified） | 该指标的证据齐全，可以给数字 |
| 待审（review item） | 缺什么证据，带文件:行号，需要人决定 |
| 举证责任（burden of proof） | 编译层必须证明范围完整，而不是算法层猜 |
| H / K 账户 | H = 真实可核对余额；K = 只有申赎累计，不当作可花/份额 |
| 用途（purpose/owner） / 类别（category） | 钱的归属（资金用途） / 消费算哪一类 |
| Q / G | 划拨目标（planned） / 实际划拨（actual） |
| `ref` / claim | 审阅决定绑定的事实引用 |
