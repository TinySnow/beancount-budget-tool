# 连续三个月的完整虚拟案例

安装项目后，在仓库根目录运行（Windows、macOS 命令相同）：

```sh
python examples/v6/acceptance/run.py --output demo-result
```

`demo-result` 必须是新目录。脚本复制本目录的虚构账本，按 `decisions.yaml` 中明确列出的虚构决定，运行首月初始化、责任认领、下一月准备与完整月报。它没有真实账本参数；真实账本要按 QUICKSTART 自行确认事实。

## 应该看到什么

| 月份 | 实际可花 | 最多能花 | 当月情况 |
|---|---:|---:|---|
| 2026-10 | 880 | 880 | 有信用卡未还 120、单位代垫待收 300 |
| 2026-11 | 1160 | 1160 | 还卡 120、报销到账 300、日常消费 20；家电另收退款 760 |
| 2026-12 | 1160 | 1160 | 没有新交易，余额继续保留，月度消费和划拨不重复计入 |

三个月均为 `CERTIFIED_SCOPED`，待审为零。单位代垫到账前不加入可花现金；还信用卡不再算一次消费；家电退款回到家电用途，不补生活费。

输出目录有每月的 `.txt`、`.json` 和配置文件。命令也会打印每个月的配置路径。继续用这些配置打开 TUI 或重算：

```sh
beancount-budget-tool --config demo-result/initial/compiled/month.yaml --format tui --tui-config demo-result/2026-11/compiled/month.yaml --tui-config demo-result/2026-12/compiled/month.yaml
```

`[`／`]` 切月份，`r` 重算，`/` 筛选。签发后按 `a` 看当月交易，再按 Enter 看逐腿分类、资金用途、责任和原始账本；待审时 Enter 仍打开待审详情。

比较三个月并导出 CSV：

```sh
beancount-budget-report --config demo-result/initial/compiled/month.yaml --config demo-result/2026-11/compiled/month.yaml --config demo-result/2026-12/compiled/month.yaml --format csv --output demo-result/quarter.csv
```

区间原支出 2101、退款 760、净消费 1341 CNY；期末最多能花仍是 1160 CNY。月末可花及余额不相加，消费目标与 Q−G 逐月比较。

## 与 REQUIREMENTS 九个例子的对应

| 例子 | 虚拟账本中的处理 |
|---|---|
| 1 | 工资 5000 先归自由资金，同账户正式划入生活费 2000。 |
| 2 | Daily 从自由资金划 700 到 Savings 的储蓄用途。 |
| 3 | Savings 支付交通 700，省略 `fund`，扣默认支出用途生活费；账户实际为零，储蓄 700、生活费 −700，月报保留警告。 |
| 4 | Mixed:A 的自由资金 700 分成储蓄 100、电子产品 200、旅游 400。 |
| 5 | 两边相同的多用途金额搬家，再单独记同账户旅游转电子产品 100。另一种混合调整写法由自动测试单独验证。 |
| 6、7 | Trip:Bank 先将旅游 500 搬到 Fund，再付酒店 461；Bank 留 100、Fund 留 39。 |
| 8 | 买家电 800，下一月退款 760；两月合计消费 40。同月退款写法也有单独测试。 |
| 9 | 完全预算外、类别预算外但使用储蓄、类别预算外但补充储蓄，分别核对。 |

为补全原例省略的前提，切换日前已明确记录 Mixed:A、旅游、家电及储蓄的虚构期初。例 4／5 与例 6／7 使用不同账户，避免把各例省略的背景混在一起。所有报告沿用同一个 `2026-10-01` cutover 和同一份期初，不逐月重新塞钱。

费用类别保留原例的独立名称：交通费用、酒店、家电与生活开销是不同根类别；生活开销消费上限 2000 仅约束它自己的子树。资金用途“生活费”与费用类别并非同一字段。此处实际可花比消费目标差更小，所以首页受实际可花约束。

用途 G 记录正式划拨／重分配，也包含普通收入显式 fund 直接分配到默认收入用途之外的部分；本例额外储蓄到账 100 也计入储蓄目标。消费、刷卡和还款不算划拨；它不等于用途资金余额。旧架构中专项消费是否调减 G 的表述仍待规范对齐，本案例不改变该口径。

## 试着制造待审

只改输出目录里的 `main.bean`，再运行对应月报命令或在 TUI 按 `r`：

- 例 4 将 `旅游400` 改成 `旅游399`：合计少 1，待审指向该分录行号。
- 例 5 只改转入一侧为 `电子产品50，储蓄250，旅游300`：总额仍是 600，但两侧用途不等，待审。
- 删掉例 2 转出分录的 `fund`：Daily 有混合用途，部分转出无法推定，待审填写表可选择来源用途。

这些情况不返回局部月报。主动划拨导致用途负数会报错，消费导致用途负数则保留已审月报和警告。

`tests/test_v6_acceptance.py` 还验证“导出待审→批准→签发→修改旧交易→定位过期决定→重新审阅→签发下一月→重跑旧月”。它只覆盖此案例中的人民币 H 账户及简单责任；K、证券池、外币和复杂债务仍由各自测试与实施状态界定。
